# 쇼츠 학습 구조 설계 (2026-08-04)

사장 지시: "카테고리별로 프롬프트를 DB에 저장하든지 해서 학습해 나가는 방향으로 하는 게
좋지 않을까? 이미지 생성 전에 글을 쓰고, 글 쓰기 전에 자료수집도 하고 트렌드 맞게
그렇게 설계돼 있니?" → 현황 실측 후 1→2→3 단계로 합의.

**★이 문서는 설계만이다. 구현 전이며, 착수 시 이 문서의 "미결 사항"부터 확정할 것.**

## 1. 현황 실측 (2026-08-04, 프로덕션 DB 직접 조회)

### 1-1. 파이프라인 순서는 이미 올바르다 (변경 불필요)

사장이 물은 "자료수집 → 글 → 이미지" 순서는 **이미 그렇게 돼 있다.**

| 단계 | 함수 | 비고 |
|---|---|---|
| ①자료수집 | `run_research()` | **실제 Google Search 툴 사용**(`types.Tool(google_search=...)`) |
| ②시나리오 5개 | `generate_scenarios()` | 리서치 반영, 100P 과금 |
| ③대본 확정 | `build_script_draft()` | 내레이션·자막·장면계획을 **텍스트로만** 완결 |
| ④이미지 생성 | `render_scene_images()` | 확정된 계획대로 생성 |
| ⑤TTS→조립→검증 | | |

★③④ 분리는 2026-07-24 재설계의 산물이다(그 전엔 한 함수에서 동시에 일어나 "즉석
재생성이 검수 없이 최종본에 들어가는" 구조였음). **이 분리를 되돌리지 말 것.**

리서치 프롬프트는 후킹 문구뿐 아니라 **화면 구성(구도 비율·색감·자막 배치)까지** 조사하고,
언어별 문화권 톤도 반영한다. 트렌드는 매 요청 실시간 검색으로 들어온다.

### 1-2. 학습 계층은 뼈대만 있고 작동하지 않는다 ← 진짜 공백

```
ShortsTrend    : 0건   ← 카테고리별 축적 트렌드
ShortsUserPref : 0건   ← 회원별 톤·금지어
```

**읽는 코드(`load_trend`, `load_user_pref`)만 있고 쓰는 코드가 0개.**
`grep -rn 'INSERT INTO "ShortsTrend"'` → 결과 없음.

결과적으로 현재 구조:
```
매 요청 → 검색비 지불 → 리서치 → 사용 → 폐기
                                    ↑ 100번 만들어도 101번째가 나아지지 않음
```

### 1-3. 리서치 보존은 2026-08-02부터 — 그 이전은 이미 소실

전체 13건 중 `researchJson`이 남은 건 **3건(birthday)뿐**. 나머지 10건은 복원 불가.
→ **소급이 안 되므로 "지금부터 남기는" 것이 최우선**이라는 근거.

### 1-4. ★승인 신호는 이미 존재한다 (설계를 크게 단순화하는 발견)

`SampleVault.sourceUserShortsId`로 "어느 원본이 어드민 승인을 받았는지" **역추적 가능**.

| UserShorts | 카테고리 | 리서치보존 | 승인됨 |
|---|---|---|---|
| 15, 22 | (none) | ✗ | **O** |
| 27 | insight | ✗ | **O** |
| 28 | wellness | ✗ | **O** |
| 29 | meme | ✗ | **O** |
| 30 | product | ✗ | **O** |
| 17,18,21,23 | (none) | ✗ | ✗ |
| 34,35,36 | birthday | **O** | ✗ |

→ **승인 6건 / 미승인 7건.** 새 컬럼 없이도 정답 라벨을 만들 수 있다.

**단, 치명적 교차 공백**: 승인된 6건은 **리서치가 없고**, 리서치가 있는 3건은 **승인이 없다.**
즉 지금 당장은 "승인 O + 리서치 O"인 학습 가능 표본이 **0건**이다.

### 1-5. 쓸 수 없는 신호 (조사했으나 배제)

| 신호 | 현황 | 판정 |
|---|---|---|
| 프리미엄 최종선택 `selectedVideoSlot` | 13건 **전부 NULL** | ✗ 아무도 프리미엄 미사용 |
| 회원 재주문 | 총 13건, 사실상 테스트 | ✗ 표본 부족 |
| 실제 유튜브 시청 성과 | 연동 없음 | ✗ 범위 밖 |

## 2. 설계 원칙 (합의된 것)

1. **1→2→3 순서.** 3번(CATEGORY_SPECS DB 이전)이 마지막인 이유: 프롬프트를 DB로 옮겨도
   **누가 그 값을 개선할지가 없으면** 코드에 있으나 DB에 있으나 같다. 개선의 근거(1·2)가
   먼저다. (단 "어드민이 즉시 손보는 운영 편의"는 별개 가치이므로 앞당길 수 있음.)

2. **★1번은 "축적"이 아니라 "축적 + 평가"로 묶는다.** 평가 없이 축적만 하면 잘된 것과
   망한 것을 구분 없이 평균 내게 되고, 실패 패턴까지 "트렌드"로 굳어 **품질이 오히려
   떨어진다.** `load_trend` 기존 주석도 같은 위험을 경고하고 있다:
   > "트렌드가 리서치를 *대체*하도록 짜면 테이블이 비었을 때 오히려 품질이 떨어진다"

3. **트렌드는 리서치를 대체하지 않고 보강만 한다** (기존 설계 유지).
   테이블이 비어도 기존 동작이 그대로여야 한다(폴백 우선).

4. **조회 실패는 삼킨다.** 학습 계층 때문에 쇼츠 제작 자체가 실패하면 본말전도.

## 3. 1단계 설계 — 축적 + 평가

### 3-1. 평가 신호 기록 (지금부터 남기기 시작)

★소급 복원이 안 되므로 **가장 먼저** 넣는다.

- 승인 신호는 `SampleVault.sourceUserShortsId` 조인으로 이미 얻을 수 있다 → **새 컬럼 불필요**
- 다만 "반려"는 기록이 없다(복사를 안 했을 뿐, 명시적 반려와 구분 불가)
- → `UserShorts`에 평가 컬럼을 추가할지는 **미결 사항 A** 참고

### 3-2. 트렌드 요약 크론 (`ShortsTrend` 채우기)

기존 스키마가 이미 학습을 염두에 두고 설계돼 있다 — **그릇은 준비돼 있다**:

| 컬럼 | 용도 |
|---|---|
| `category` | 카테고리별 분리 |
| `trendMd` | 축적된 지식(프롬프트에 얹히는 본문) |
| `sourceNote` | **어떤 근거로 얻었는지** |
| `sampleCount` | **몇 건에서 뽑았는지** |
| `isActive` | 활성 버전(과거 버전 보존하며 교체) |

동작:
1. 카테고리별로 **승인된 건의 `researchJson`만** 모은다
2. LLM으로 "이 카테고리에서 반복적으로 통한 패턴"을 요약
3. 기존 활성 행을 `isActive=false`로 내리고 새 행 삽입(버전 보존 — 나쁘면 되돌릴 수 있어야 함)
4. `sampleCount`·`sourceNote`에 근거를 남긴다

**읽는 쪽(`load_trend`)은 이미 구현돼 있어 손댈 필요 없다.** 쓰는 쪽만 만들면 즉시 작동.

### 3-3. ★1단계의 현실적 한계 (반드시 인지할 것)

**"승인 O + 리서치 O" 표본이 현재 0건이다** (§1-4). 즉 크론을 지금 만들어도
**당장 요약할 재료가 없다.** 그래서 1단계의 진짜 가치는:

- 트렌드 요약 크론을 "돌려서 효과 보기"가 아니라
- **지금부터 신호와 원재료를 빠짐없이 남겨서, 표본이 쌓이면 저절로 작동하게 하는 것**

→ 크론에 **최소 표본 수 가드**를 반드시 넣는다(예: 승인 3건 미만이면 요약 생략).
   적은 표본으로 만든 트렌드가 프롬프트에 얹히면 편향만 증폭된다.

## 4. 2단계 설계 — 신호 축적 후

- 트렌드 버전별 **승인율 비교**(A/B): `isActive` 교체 시점을 기록해두면 버전별 성과 비교 가능
- 가중치: 최근 건 우선, 카테고리별 표본 수에 따른 신뢰도 반영
- ★2단계는 **1단계 데이터가 쌓인 뒤** 실제 분포를 보고 설계한다(지금 미리 정하지 않는다)

## 5-2. ★확정된 전체 작업 순서 (2026-08-04, 사장 지시)

학습 구조(위 1~3단계)와 **카테고리별 구조 개편**이 같은 파일(`CATEGORY_SPECS`)을
건드리므로 순서를 합쳐서 확정했다. 사장 지시: "실물확인 안전망 이미지 대본 디비이전
순서로 다시 하자".

| 순서 | 작업 | 상태 |
|---|---|---|
| ① | **실물 확인** — `4df64f9`(소품 안전망) 수정이 실제 완성본에 반영되는지 | 진행 중(#37) |
| ② | **안전망 분리** — 카테고리별로 어떤 안전망이 도는지 한 곳에서 선언 | 대기 |
| ③ | **이미지 로직 분리** — `render_scene_images`의 모드별 분기 | 대기 |
| ④ | **대본 로직 분리** — `build_script_draft`(분기 29개, 최대 덩어리) | 대기 |
| ⑤ | **DB 이전** — 정리된 구조를 통째로 DB로 + 어드민 편집 UI | 대기 |

**왜 구조 정리(②③④)가 DB 이전(⑤)보다 먼저인가**: 지금 상태로 DB에 옮기면 흩어진
분기 53개는 코드에 남은 채 tone만 DB로 가서, **정작 사고 나는 규칙은 그대로 코드에
남는다.** 구조를 먼저 정리하고 옮겨야 일이 두 번 되지 않는다.

**왜 실물 확인(①)이 먼저인가**: 2026-08-03에 프롬프트만 고치고 "됐겠지" 했다가 재발했고,
08-04에도 대본까지만 확인하고 "됐다" 했다가 또 틀렸다(#36). **두 번 다 실물 확인을
건너뛴 게 원인.** 미검증 수정 위에 구조 개편을 얹으면 나중에 문제가 생겼을 때
"소품 수정이 틀렸나, 구조 개편이 깨뜨렸나"를 가릴 수 없다.

### 구조 개편 실측 근거 (2026-08-04)

```
카테고리 분기 53개가 7개 함수에 흩어져 있음
  build_script_draft   29개   ← ④단계 대상(최대)
  render_scene_images   8개   ← ③단계 대상
  build_preview_video   4개
  _produce_one_video    4개
  run_admin_topic       3개
  _verify_final_video   2개
  process_produce       1개
```

`CATEGORY_SPECS`는 이미 있지만 담는 것은 `needs_topic / research_kind /
scenario_kind / tone` 4개뿐 — **말투와 리서치 종류만** 관리하고, 정작 사고가 나는
**안전망·이미지 배정·세그먼트 구성 규칙은 전부 함수 안 if문**에 있다.

### ★근본 원인: `isProduct`가 두 가지 뜻으로 혼용된다

`script["isProduct"]`는 원래 "상품이다"였는데, 생일축하에서 **"실물을 자르지 마라"**
라는 뜻으로 필드를 재사용했다(1005행, 주석에도 "'상품'이라는 이름과 뜻은 다르지만"
이라고 적혀 있음). 그 결과 `render_scene_images`의 상품 안전망이 생일축하에도 돌아
**코드로 강제 배정한 소품 scene_prompt를 지웠다**(#36 사고).

②단계에서 이 플래그를 **의도별로 분리**하는 것이 핵심이다:
- "실물 사진을 크롭하지 마라"(생일·상품 공통)
- "AI 재생성을 금지하라"(상품 전용)
- "콜라주를 금지하라"(캡처 전용)

현재는 이 셋이 `isProduct` 하나에 뭉쳐 있고, 조건문에 특례를 계속 덧붙이는 방식
(`isProduct or category=='birthday'`, `if seg.get("_autoScene"): continue`)으로
땜질돼 있다. **같은 문제를 이미 두 번 겪은 흔적**이라 구조로 풀어야 한다.

## 6. 미결 사항 (착수 전 확정 필요)

**A. 반려 신호를 명시로 기록할 것인가?**
   지금은 "승인 안 됨"과 "아직 검토 안 함"이 구분되지 않는다. `UserShorts`에
   `reviewVerdict`(approved|rejected|null) 같은 컬럼을 둘지, 아니면 SampleVault 조인만으로
   충분하다고 볼지. → 어드민 UI 작업량과 직결.

**B. 트렌드 요약 주기와 트리거**
   크론(주 1회?) vs 승인 건수 임계 도달 시. 표본이 적은 초기엔 주기 크론이 헛돌 수 있다.

**C. 최소 표본 수 가드의 임계값**
   승인 3건? 5건? 너무 낮으면 편향, 너무 높으면 영영 안 돌아간다.

**D. 3단계를 앞당길 것인가**
   "학습 근거가 먼저"라는 이유로 3순위지만, **어드민이 즉시 프롬프트를 손보는 운영 편의**는
   학습과 무관한 별개 가치다. 사장이 이 편의를 우선하면 순서 조정 가능.
