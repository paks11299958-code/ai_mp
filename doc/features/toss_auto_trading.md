# 토스증권 자동매매 봇

토스증권 Open API로 주식을 자동매매하는 봇 `~/toss_trader/`(서버1 pm2) + 어드민 '토스 자동매매' 모니터 탭. **현재 DEBUG(드라이런) = 실주문 0.** (최종 2026-07-04)

## 안전 설계 (최우선)

- **MODE=LIVE 를 정확히 명시했을 때만 실거래.** 그 외 전부 DRY_RUN(기본이 안전). 실제 주문 POST는 `broker._live_post_order` 한 곳뿐.
- 써킷브레이커(`risk.py`): 1회 금액/수량 상한 · 시간창 과도주문 자가 HALT · 일손실 한도(절대금액+%) · 연속손절 차단 · 변동성 필터. SIGINT/SIGTERM 시 미체결 전량취소 후 종료.
- **토스 API는 샌드박스 없음 = 실자산 전제.** IP 화이트리스트=서버1(34.50.27.95)만 등록 → **봇 실행은 서버1**(서버2는 403).

## 모듈 구조 (`~/toss_trader/`)

| 파일 | 책임 |
|---|---|
| `config.py` | 설정 로더(단일 게이트). ★MODE=LIVE 아니면 DRY_RUN. dotenv 없는 서버1용 폴백 파서. 종목명 매핑(SYMBOL_NAMES). |
| `broker.py` | 토스 API 클라이언트(OAuth2·시세·캔들·계좌·주문). ★DRY_RUN 게이트. `get_avg_price`·`refresh_token`. |
| `strategy.py` | 매매 전략(교체 가능 Protocol). **ScoreTrendStrategy**(점수형 추세추종) + SmaCross(예시, 보존). |
| `risk.py` | 리스크 매니저/써킷브레이커. 사전검사 + 손익/연속손절/변동성. |
| `executor.py` | 신호→리스크 관문→주문. 변동성 필터(매수만), 실패 시 미체결 동기화. |
| `main.py` | 조립+루프. 시장캔들·평단 조회해 전략에 전달. 로그/status 기록. |
| `status_writer.py` | 상태를 `logs/status.json`에 원자적 기록(어드민 조회용). |

## 전략: 점수형 추세추종 (2026-07-04, 로드맵②)

**일봉 스윙** 전략. 단타(체결강도·호가·수급·VI)는 토스 API 한계로 배제(REST만, WebSocket 없음).

### 매수 — 조건별 점수 합산 ≥ 임계(기본 80)이면 BUY

| 조건 | 배점 |
|---|---|
| MA20 > MA60 (정배열) | +25 |
| 종가 > MA120 | +20 |
| 거래량 > 20일 평균 × 2 | +20 |
| RSI 40~60 | +15 |
| 20일 최고가 돌파 | +10 |
| 시장 상승 (KODEX200 MA20>MA60) | +10 |

- **시장 필터 = KODEX200 ETF(069500) 프록시.** 토스는 코스피 지수를 조회 못 하므로(KOSPI/KS11 등 전부 실패) 대표 ETF를 프록시로 사용. 시장 캔들 없으면 그 10점은 제외(90점 만점).
- MA120 계산 위해 캔들 `count=150`.

### 매도 (보유 중일 때만, 평단 필요)

- 손절 −3% · 익절 +8% · 종가 < MA20(추세 이탈)
- 보유 여부/평단은 봇(`main`)이 `broker.get_avg_price`로 조회해 전략에 전달 → 전략은 순수 판단만.
- ★평단 item 필드명 **실측 완료**(2026-07-30, 보유 2종목 기준): `averagePurchasePrice`(평단) ·
  `lastPrice`(현재가) · `quantity` · `name` · `profitLoss.{amount,rate,amountAfterCost,rateAfterCost}`.
  금액은 문자열이고 일부는 `{krw,usd}` 중첩이라 파싱 방어 필요. `holdings_json.py`가 이 매핑을 담당.

## 리스크 차단 (4단계, `risk.py`)

- **연속손절** N회(기본 3, 익절 시 리셋) → 그날 매매 종료(HALT)
- **%기준 일손실** 자산 대비 3%(절대금액 한도와 병행, `set_equity`로 자산 반영)
- **변동성 필터** 일일 (고−저)/저 ≥ 15% 종목 진입 거부(매수에만 적용)
- ★**1회 수량·금액 상한은 매수에만 적용**(2026-07-30 수정, `check_order`에서 `side != "SELL"` 가드)

### ★사고 이력 — 금액상한이 손절을 막았다 (2026-07-30)

`MAX_ORDER_AMOUNT_KRW=600000`이 **매도에도** 적용돼 손절이 **07-20~30 누적 5,369회 거부**됐다.
전략은 매일 `신호=SELL 손절 -10.5%`를 냈지만 `리스크 거부: 금액 초과: 652,400원 > 상한 600,000원`.

- **원인**: 7/16 균등배분(`EQUAL_ALLOC=1`) 도입으로 종목당 예산이 커졌는데(총자산÷보유수)
  1회 주문 상한 60만은 그대로 뒀다. 매수는 50/30/20 분할이라 안 걸리고 **매도는 전량이라 걸렸다.**
- **왜 SELL을 면제하는가**: 상한의 목적은 "실수로 과도하게 **사는** 것" 방어다. 청산은 리스크를
  **줄이는** 행위라 막을 이유가 없다 — 막으면 상한이 오히려 손실을 무한정 키우고, 주가가 올라
  주문금액이 상한을 넘으면 **익절도 막혀** 수익 확정조차 못 한다.
- 일손실 한도·연속손절·과도주문 정지는 SELL에도 그대로 적용된다(청산만 면제).
- 이 사고는 **아침 보고 버그와 겹쳐** 10일간 발견되지 않았다(아래 참조). -5% 손절선이 -11.6%까지.

### ★아침 보고가 손절신호를 "보유 유지"로 표시했다 (2026-07-30)

보유 재점검이 `avg_price=None`으로 채점해 **청산 판정 자체를 못 했다.** 실측 대조:

| 호출 | 결과 |
|---|---|
| `avg_price=None` | `HOLD` — "진입보류(하락)" |
| `avg_price=104100` | `SELL` — "손절 -11.2%" |

★진짜 문제는 **말뜻이 뒤바뀐 것**: "진입보류 = 새로 사지 마라"인데 화면이 `HOLD → "보유 유지"`로
번역해 **"들고 있어라"로 읽혔다.** 사장은 매일 "보유 유지"를 보고 안 팔았고, 같은 시각 봇은
SELL을 외치며 거부당했다.

- **수정**: `score_json.py`에 `<코드>:<평단>` 형식 신설(하위호환 유지) → 보유는 평단을 넘겨 판정.
  문구도 `HOLD → "관망 — 신규 진입 보류"`, `SELL → "🔴 매도 신호(청산)"` + 손익·사유 표시.
- **교훈**: 보유 종목을 **신규 진입 관점 점수로 판단하면 안 된다.** 청산 판정에는 평단이 필수다.

## 설정 (★설정처 주의)

- **실제 종목/모드 설정처는 `config.env`가 아니라 `ecosystem.config.js`의 `env`.** config.py 폴백 파서가 "이미 있는 환경변수는 안 덮어씀"이라 pm2 env가 우선.

## 📐 [설계만, 미구현] 매매 결과 자기학습 — 2026-08-03

사장 지시: "매수 매도 시 결과를 학습해서 추후 매수 매도에 반영하는 자기학습 설계를
해놔라 — 일단 설계만 해놓고 추후 할 일에 기록." **아래는 설계뿐이며 코드는 아직
한 줄도 안 건드렸다.** 실행 우선순위·착수 시점은 별도 지시 대기.

### 왜 지금 바로 못 만드나 — 선행 공백

`ScoreTrendStrategy`(`strategy.py`)의 채점 가중치(MA20/60/120·거래량·RSI·신고가·
시장추세, `self.w`)와 손절(-3%)·익절(+8%)·매수임계(80)는 이미 파라미터화는 돼
있다(`config.py` env → 생성자 인자). "학습"이 가능하려면 이 파라미터들을 **결과와
연결해 평가**할 수 있어야 하는데, 현재 `logs/pnl_ledger.json`은 **일자별 실현손익
합산치**만 가지고 있고 "이 매수는 어떤 점수·어떤 근거로 진입해서 어떻게 끝났는가"를
매매 1건 단위로 기록하는 구조가 없다(`orders.log`는 텍스트 로그라 집계 불가). 즉
**1단계(이력 적재)를 먼저 만들지 않으면 학습 자체가 성립하지 않는다.**

### 설계: 4단계 파이프라인

```
①이력 적재 → ②주간 배치 분석 → ③파라미터 제안(사람 승인 대기) → ④승인 시 적용
```

**① 이력 적재 — `logs/trade_history.jsonl`(신규, 매매 1건당 1줄)**
매수 체결 시점에 진입 스냅샷을, 청산 체결 시점에 결과를 같은 레코드에 병합 기록:
- 진입: 종목코드, 진입시각, 체결가, 수량, **진입 당시 채점 상세**(`strategy.py`
  `add()`가 이미 항목별 점수를 갖고 있으므로 합계뿐 아니라 `{ma_trend: 25,
  volume: 20, rsi: 15, ...}` 항목별로 남긴다 — 나중에 "어느 지표가 실제로 수익에
  기여했는지" 항목 단위 분석이 가능해야 하므로), 진입 사유(수동/자동편입/발굴직접),
  당시 매수임계값.
- 청산: 청산시각, 청산가, 청산사유(손절/익절/추세이탈/수동), 보유기간(일), 실현손익
  (금액·%), 청산 당시 파라미터(손절%·익절%가 그 사이 바뀌었을 수 있으므로 스냅샷
  고정).
- 기록 위치는 `ledger.add_realized()`(청산)·매수 체결부(`executor.py` 또는
  `main.py` 매수 분기) 양쪽에 훅을 추가하는 구조 — 기존 `pnl_ledger.json` 갱신
  로직 옆에 나란히 적재(기존 구조 안 건드림, append-only라 회귀 리스크 낮음).

**② 주간 배치 분석 — 서버2 크론(신규, 예: 매주 월요일 07:00)**
`trade_history.jsonl`을 모아 매매 건수가 통계적으로 의미 있는 최소치(예: 20건)
이상일 때만 분석 시작(적은 표본으로 파라미터를 흔들면 과적합·노이즈 반영 위험):
- 항목별 점수와 실현손익의 상관(어느 지표가 높을 때 실제로 수익이 났는지),
  손절·익절 도달 비율(익절 전에 손절되는 비율이 과도하게 높다면 손절선이 타이트한
  신호), 보유기간별 손익 분포(단타/스윙 중 어느 쪽이 더 잘 맞았는지 — 이 봇은
  현재 보유기간 상한이 없어 이미 데이터가 섞여 있음).
- 산출물은 **"현재 임계 80 → 데이터상 75가 승률·손익비 더 좋음" 같은 제안 값 +
  근거(표본 수·백테스트 비교)** 텍스트. 이 결과를 텔레그램/일일 보고에 요약 첨부
  (기존 15:40 마감분석·07:00 아침보고 크론과 같은 통로 재사용 — `chaewon_stock_
  cron.py`).

**③ 파라미터 제안 — 사람 승인 대기 (자동 반영 안 함)**
`project_toss_trader_ops.md`의 기존 합의(완전 자율화 보류, 종목편입만 우선
자동화)와 정합성을 맞춘다 — **학습 결과가 임계·손절·익절을 자동으로 바꾸는 것은
이번 설계 범위 밖.** 제안값을 어드민 화면(신규 패널 또는 기존 `TossTraderPanel`
확장)에 "적용" 버튼과 함께 표시하고, 사장이 확인 후 눌러야 `selection.json`의
`params`에 반영되는 구조로 설계 — 위험작업 비밀번호 게이트(`requirePassword()`)도
동일하게 적용(2026-08-03 401 버그 교훈: 새 위험작업 버튼은 처음부터 이 패턴 확인).

**④ 승인 시 적용 + 효과 재검증**
적용 후에도 계속 ①②가 돌아가므로, "파라미터를 바꾼 뒤 실제로 승률·손익비가
개선됐는지"를 다음 주기 분석에서 자동으로 비교(적용 전/후 구간을 나눠 표시) —
효과가 없거나 나빠지면 되돌리자는 판단도 사람이 하도록 제안에 포함.

### 단계적으로 잡은 이유

- 표본 부족 위험: 지금 LIVE 매매 건수가 적어(코웨이·한국콜마 수동 고정 + 자동편입
  시작 직후) 당장 분석해도 통계적 의미가 약하다 — ①을 먼저 쌓는 기간이 필요.
- 기존 운영 원칙([[project_toss_trader_ops]] ⑩)과의 정합성: "손절·익절까지 AI가
  자율 판단"은 이미 한 번 논의해서 보류한 범위라, 이번 설계도 **자동 적용이 아니라
  제안까지만**으로 그 합의선을 넘지 않게 잡았다.
- 안전망 우선: 매매 로직 자체(`strategy.py`)를 학습 결과가 직접 건드리게 하면
  회귀 시 실거래 손실로 바로 이어진다 — 이력 적재는 append-only라 리스크가 거의
  없지만, 파라미터 반영은 되돌리기 어려운 자산 리스크이므로 사람 승인 게이트를
  구조적으로 박아둔다.

  막힌 건 장기추세(MA120)였다. **종목마다 막히는 항목이 다른데 일반화한 것이 오판.**
  공통 병목은 오히려 `시장 상승`(KODEX200 MA20>MA60) — 충족률 5%로, **지금 시장 자체가
  하락 국면**이라 개별 종목이 아무리 좋아도 못 넘는 벽이다(의도된 안전장치로 보인다).
- **NXT(넥스트레이드) 손절매도**: 착수 직전 중단(코드 변경 0, 백업만 `*.bak_nxt_20260804`).
  - "장 마감 후 발굴" 자체는 **검증 결과 타당** — 발굴가 대비 익일 시가 갭이 평균
    **-0.61%**로 작아 "장 끝나고 뽑으면 늦는다"는 우려는 데이터상 기우였다.
    오히려 장중 발굴은 확정봉 원칙과 충돌한다(거래량·신고가가 계속 변해 종목이 오락가락).
  - 현재 NXT는 **시세만** 쓴다(`clock.is_nxt_hours`, 평일 08~20시, `priceBasis: "nxt"`).
    주문은 `MARKET_HOURS_ONLY=1`로 **평일 09:00~15:30만**. 발굴 스캔·긴급정지는 장외에도 활성.
  - 매수까지 NXT로 여는 건 반대 — 전략이 **일봉 지표 기반**이라 거래창을 넓혀도 같은
    판단을 더 오래 들고 있는 것뿐이고, NXT는 유동성이 얇아 슬리피지가 크다.
    `place_order`도 KRX 호가단위로 스냅하게 돼 있어 거래소 지정 파라미터부터 필요하다.
  - 사장 지적으로 중단: **"손절이 너무 작으면 조그만 흔들림에도 손절 치는 거 아냐?"**
    → 타당하다. 익일 고가가 평균 **+3.7%**까지 갔다 종가 +0.57%로 되밀리는 것을 보면
    **손절 3%는 일중 변동폭 안에 들어 있다.** NXT는 호가가 더 벌어져 헛손절이 늘어난다.
