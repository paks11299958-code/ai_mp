> 작성 2026-08-05 · 상태: **1단계 구축 완료(실측 검증됨)** · 사장 결정은 §7
> 사장 결정(2026-08-05): ①**온디맨드**(Spot 검토 후 철회) ②디스크 **200GB**
> ③4시간 상한 + **★큐 활용** ④**서비스 연동**
> 사장 지시: "AI 스튜디오를 구축하려는데 GCP 서버 임대할 거고, **사용할 때만 켰다 껐다** 할 거다."

## 1. 무엇을 만드는가

**이미지 생성을 직접 돌리는 GPU 서버**를 두되, 쓸 때만 켜서 비용을 최소화한다.

지금은 이미지 생성을 전부 외부 API(gemini-3.1-flash-image, gpt-image-2)로 처리한다.
자체 GPU를 두면:

- **원가 절감** — 장당 과금이 사라지고 시간당 과금으로 바뀐다(대량 생성일수록 유리)
- **모델 자유도** — SDXL·Flux·LoRA 등 원하는 모델을 직접 올려 쓴다.
  API가 막는 화풍·구도 제약에서 자유롭다
- **실험 가능** — 프롬프트를 수십 장씩 돌려보는 실험이 부담 없어진다

★단, **외부 API를 대체하는 게 아니라 병행**한다. 한글 텍스트 렌더링(gpt-image-2)처럼
API가 확실히 나은 영역이 있고, 서버가 꺼져 있을 때도 서비스는 돌아야 한다.

## 1-1. 서버 구성에서의 위치

| 역할 | 서버1 (운영) | 서버2 (에이전트) | **서버3 (AI 스튜디오)** |
|---|---|---|---|
| 상시 가동 | ✅ | ✅ | ❌ **큐에 일이 있을 때만** |
| PostgreSQL | ✅ 보유(도커) | 접속만 | **접속만** |
| GPU | ❌ | ❌ | ✅ **L4 24GB** |

| 과금 | 상시 | 상시 | **가동시간 + 디스크** |

★서버3 은 **꺼져 있는 것이 기본 상태**다. 이 점이 서버1·2 와 근본적으로 다르고,
감시·운영 설계가 전부 여기서 갈린다(§5).

## 2. 사양 — 무엇을 얼마에 빌리나

### 2-1. 결론: `g2-standard-4` (NVIDIA L4 24GB)

| 항목 | 사양 |
|---|---|
| 머신 | g2-standard-4 — vCPU 4, RAM 16GB |
| GPU | **NVIDIA L4 24GB VRAM** |
| 리전 | asia-northeast3 (서울) — 기존 서버1·2와 같은 리전 |

**왜 L4인가**: SDXL은 8GB, Flux 양자화판은 8~12GB, Flux 풀버전은 16~24GB를 쓴다.
L4의 24GB면 **Flux 풀버전까지 여유 있게** 돌아간다. 상위 A100(40GB)은 시간당
$3.67로 5배 비싼데, 이미지 생성엔 과잉이다.

**왜 T4가 아닌가**: T4는 15GB에 Tensor Core 세대가 낮아 SDXL에서 2~3배 느리다.
켜져 있는 시간만큼 돈이 나가는 온디맨드에서는 **느린 GPU가 오히려 비싸다.**

### 2-2. 가격 (2026-08 기준, 서울 리전)

| 구분 | 시간당 | 비고 |
|---|---|---|
| **온디맨드** ⭐확정 | **$0.9077** (약 1,260원) | 중단 없음, 호스트 점검 시 자동 이전 |
| Spot VM | $0.2709 (약 375원) | 70% 할인이나 30초 예고 후 중단 — **§4에서 철회** |

★**서울 Spot이 미국보다 싸다**($0.27 vs us-central1 $0.40). 리전을 옮길 이유가 없고,
기존 서버와 같은 리전이라 내부 통신도 유리하다.

### 2-3. ★꺼도 나가는 돈 — 디스크

**인스턴스를 꺼도 디스크 요금은 계속 나간다.** 온디맨드 설계의 핵심이다.

| 디스크 | 월 단가 | 200GB 기준 월 |
|---|---|---|
| Balanced PD | $0.10/GB | $20 (약 2.8만원) |
| SSD PD | $0.17/GB | $34 (약 4.7만원) |

모델 파일이 크다. 실측 기준 용량:

| 항목 | 용량 |
|---|---|
| OS·CUDA·ComfyUI | 15GB |
| Flux.1-dev **fp16 풀세트**(체크포인트 23 + T5-XXL 9.2 + CLIP 1.6 + VAE) | 약 34GB |
| SDXL base + refiner | 13GB |
| LoRA·컨트롤넷 | 8GB |
| 생성물 임시 | 10GB |
| **합계** | **약 80GB** |

**200GB 확정**(사장 결정). 100GB로도 fp8 양자화판이면 되지만(합계 69GB), 200GB면
**Flux fp16 풀버전까지 여유**가 있고 모델을 늘릴 여지가 생긴다.
★디스크는 **줄일 수 없다** — 늘리기만 되므로 처음에 여유를 두는 판단이 맞다.

## 3. 비용 시뮬레이션 — 주 5~10시간 사용 기준

사장 예상 사용량(주 5~10시간 = **월 20~40시간**)으로 계산한다.

| 구성 | 월 20시간 | 월 40시간 | 비고 |
|---|---|---|---|
| **온디맨드 + 200GB Balanced** | **약 6.3만원** | **약 9.8만원** | ⭐확정 |
| (참고) Spot + 200GB | 약 3.8만원 | 약 4.9만원 | §4에서 철회 |
| 온디맨드 24시간 상시 | **약 92만원** | — | 참고: 안 끄면 이렇게 된다 |

계산: 온디맨드 $0.9077 × 시간 × 1,390원 + 디스크 $20 × 1,390원

**핵심**: 상시 가동 대비 **월 92만원 → 4만원대**로 떨어진다. 온디맨드의 실익이 크다.

★단 디스크 2.8만원은 **한 시간도 안 써도 나간다.** 월 사용이 10시간 미만으로
떨어지면 디스크가 비용의 대부분이 되므로, 그때는 **모델을 GCS에 넣고 디스크를
줄이는** 구조를 검토한다(다만 기동 때마다 모델을 내려받아야 해 부팅이 길어지는
트레이드오프가 있다).

## 4. Spot vs 온디맨드 — 온디맨드로 확정

처음엔 Spot(시간당 375원, 70% 할인)을 권했고 사장도 1차로 Spot을 선택했으나,
**논의 끝에 온디맨드로 철회**했다. 근거를 남긴다.

### 4-1. Spot 이 무엇인가

GCP 데이터센터의 **남는 서버를 싸게 빌려주는 것**. 대신 정가(온디맨드) 손님이
오면 **30초 예고 후 강제 종료**된다(선점, preemption). 우리가 잘못해서가 아니라
계약 조건 자체가 "자리 나면 비켜준다"이고, 그 대가가 70% 할인이다.

### 4-2. 비용 차이 (월 30시간 기준)

| 방식 | GPU 요금 | 디스크 | **월 합계** |
|---|---|---|---|
| Spot + 끄기 | 약 1.1만원 | 2.8만원 | **약 4만원** |
| **온디맨드 + 끄기** | 약 3.8만원 | 2.8만원 | **약 6.6만원** |
| 온디맨드 + 안 끄기 | 90.7만원 | 2.8만원 | **약 93만원** ❌ |

★**차이는 월 1.6만원뿐이다.** 그리고 위 표가 보여주듯
**"끄는 것"이 절감의 90%를 차지한다** — Spot 여부는 나머지를 더 줄이는 것에 불과하다.

### 4-3. 왜 온디맨드인가 (사장 판단)

**"온디맨드가 스트레스 덜 받겠다. 잘 끄면 되는 거잖아."**

| | Spot | 온디맨드 |
|---|---|---|
| 켜려는데 자리 없음 | 있을 수 있음 | **없음** |
| 작업 중 갑자기 종료 | 있음 | **없음** |
| 호스트 점검 시 | 종료됨 | **다른 하드웨어로 자동 이전** |
| 월 비용 | 4만원 | 6.6만원 |

★**만들지 않아도 되는 것이 생긴다**(이게 실질적으로 더 큰 이득):
- 30초 선점 신호 핸들러
- 죽기 전 job 을 `pending` 으로 되돌리는 처리
- `processing` 박제 회수(20분 타임아웃)
- Spot 실패 시 온디맨드 폴백 + **되돌리기**

특히 마지막이 위험했다. 폴백으로 온디맨드 전환하면 그 설정이 **남아서**, 되돌리는
처리를 빠뜨리면 **모르는 사이 3.4배 요금이 계속 나간다.** 게다가 Spot 으로 만든
인스턴스를 온디맨드로 전환할 수 있는지 자체가 미확인이었다(콘솔에 "선택한 후에는
변경할 수 없습니다" 표기). 안 되면 인스턴스를 2개 두어야 하고 **디스크도 2개**라
월 5.6만원 — 1.6만원 아끼려다 배보다 배꼽이 커진다.

→ **월 1.6만원으로 "언제 죽을지 모른다"는 걱정과 관리 코드 4종을 없앤다.**

### 4-4. 재검토 조건

실사용이 **월 100시간을 넘기면** Spot 차이가 월 5만원 이상으로 벌어진다.
그때는 실사용 데이터가 있으니 판단도 정확해진다 — 그 시점에 다시 본다.

## 5. 어떻게 켜고 끄나 — 운영 설계

### 5-1. 켜기: 어드민 버튼 한 번

```
어드민 [AI 스튜디오] 탭
  [🟢 서버 켜기]  ← 누르면 gcloud compute instances start
       ↓ 약 40~60초 (부팅 + ComfyUI 기동)
  [열기] 버튼 활성화 → ComfyUI 화면으로 이동
```

★**터미널을 안 열어도 되게** 만드는 게 핵심이다. 매번 SSH로 켜야 하면 결국 안 쓰게 되고,
켜둔 채 잊어버려 요금이 샌다.

### 5-2. 끄기: 자동이 정본, 수동은 보조

**★자동 종료가 이 기획의 성패를 가른다.** 끄는 걸 사람에게 맡기면 반드시 잊는다.

3중으로 건다:

1. **유휴 감지 자동 종료** (주 방어)
   서버 안에서 30분마다 확인 → ComfyUI에 최근 30분간 요청이 없으면 스스로 shutdown
2. **최대 가동시간 상한** (보조)
   켠 지 4시간이 지나면 무조건 종료. 유휴 감지가 고장나도 하루 최대 4시간으로 막힌다
3. **일일 점검 알림** (감시)
   매일 3시간 상태보고(monitor.js)에 **AI 스튜디오 상태**를 추가 —
   켜져 있으면 "🟡 AI 스튜디오 가동 중 (2시간 30분째)"로 보고

★교훈 적용: 07-31 토스봇이 손실한도로 멈췄는데 알림이 0건이라 다음날까지 몰랐다.
**"꺼져 있는 게 정상"인 자원은 켜져 있을 때 반드시 눈에 띄어야 한다.**

### 5-0. ★서버3은 어떻게 통신하나 — API가 아니라 **DB 큐 공유**

AI 스튜디오 서버를 **서버3**이라 부른다(서버1=운영, 서버2=에이전트).

```
[서버1] shared-api                    [서버3] AI 스튜디오 (GPU)
   │                                        │
   │ ① GpuJob 테이블에 INSERT (pending)      │
   ▼                                        │
┌──────────────────────────┐                │
│  PostgreSQL (서버1 도커)   │◀───────────────┘
│  GpuJob 큐                │   ② 워커가 직접 SELECT ... FOR UPDATE
└──────────────────────────┘   ③ 결과를 직접 UPDATE (completed)
         ▲
         │ ④ 디스패처(서버2 크론 */2)가 큐를 보고
         │    pending 있으면 서버3 start / 비면 stop
    [서버2] 에이전트
```

★**서버1이 서버3을 호출하지 않는다.** 서버3이 스스로 일어나 일감을 가져간다.

**왜 API가 아닌가**

| | API 호출 방식 | **DB 큐 방식(채택)** |
|---|---|---|
| 서버3이 꺼져 있으면 | 요청 실패 — "기능이 죽었다" | 큐에 쌓였다 나중에 처리 |
| Spot 이 갑자기 죽으면 | 처리 중 요청 유실 | `pending` 복귀 → 재처리 |
| 서버3 IP 가 바뀌면 | 서버1 설정 수정 필요 | 무관(서버3이 붙는 쪽) |
| 서버3 추가/제거 | 서버1 코드 변경 | 그냥 붙였다 떼면 됨 |

**서버3은 켜졌다 꺼졌다 하는 존재**다. 서버1이 서버3을 호출하는 구조면
"꺼져 있을 때 어떡하나"가 영원히 따라다닌다. 반대 방향이면 그 질문 자체가 없다.

**★이미 검증된 패턴이다** — 쇼츠 만들기·전자책·주식분석·홈페이지가 전부 이 방식이다
(shared-api 가 테이블에 적재 → 서버2 워커가 폴링). 서버2 는 이미 서버1 DB 를
직접 읽고 쓴다. 서버3 도 같은 방식이면 **새로 만들 통신 계층이 없다.**

**서버3 에 필요한 접근 권한**

| 대상 | 용도 |
|---|---|
| 서버1 PostgreSQL (`10.178.0.2:5432`) | `GpuJob` 큐 읽기·쓰기 |
| GCS 버킷 | 생성 이미지 업로드 |
| GCP Compute API (자기 자신) | 유휴 시 스스로 shutdown |

★DB 접속은 **내부 IP**로만 연다(공인 IP 노출 금지). 서버2 가 이미 같은 방식으로
붙고 있으므로 방화벽 규칙을 그대로 따른다.

### 5-4. ★큐 기반 운영 — 이 기획의 중심축 (사장 결정)

**켜고 끄는 걸 사람이 판단하지 않는다. 큐에 일이 있으면 켜고, 비면 끈다.**

```
회원/어드민이 이미지 생성 요청
   ↓  즉시 "접수됐습니다" 응답 (기다리지 않음)
GpuJob 큐에 적재 (status=pending)
   ↓
[디스패처] 서버2 크론 2분마다
   · 큐에 pending 있음 + 서버 꺼짐 → gcloud instances start
   · 큐 비어 있음 + 서버 켜짐    → 유휴 30분 뒤 자동 종료
   ↓
[GPU 워커] 서버 안에서 큐를 폴링해 순서대로 처리
   ↓  완료 시 결과 저장 + 텔레그램/화면 알림
```

**큐가 해결하는 것 3가지**

1. **연동 가능해짐** — 회원이 1분을 기다릴 필요가 없다. 접수만 하고 결과는 나중에.
   (쇼츠·전자책·주식분석이 이미 이 방식 — 검증된 패턴)
2. **장애에 강해짐** — 서버가 어떤 이유로든 죽어도 큐의 job 은 `pending` 으로
   되돌려 다음 기동 때 다시 처리한다. **일이 사라지지 않는다.**
   (온디맨드라 선점은 없지만, 재부팅·OOM·워커 크래시는 여전히 일어난다)
3. **가동시간이 저절로 최소화됨** — 일이 몰리면 한 번 켜서 몰아 처리하고 끈다.
   요청 5건을 각각 켜고 끄면 부팅 5회지만, 큐면 1회다.

**★4시간 상한과 큐의 관계**: 상한에 걸려 종료돼도 남은 job은 `pending`으로 남아
다음 기동에 이어서 처리된다. 상한이 작업을 잃게 만들지 않는다.

**필요한 것**
- `GpuJob` 테이블 (id, type, payloadJson, status, resultJson, createdAt, startedAt)

  (Spot이 30초 예고로 죽으면 job이 `processing`에 박제되는데, 이걸 안 풀면
  그 요청은 영원히 처리되지 않는다)

### GPU 큐 워커 (`~/gpu_worker.py`, systemd `gpu-worker`)

`GpuJob` 을 폴링해 ComfyUI 로 처리한다. 기존 큐 워커들과 같은 신뢰 모델:
원자적 상태 전이(`FOR UPDATE SKIP LOCKED`) · 멱등 · stale 회수.

**payload 형식**(모두 선택, 없으면 안전한 기본값):
```json
{"prompt":"...", "negative":"...", "width":1024, "height":1024,
 "steps":28, "cfg":7.0, "seed":123, "sampler":"dpmpp_2m",
 "model":"sd_xl_base_1.0.safetensors"}
```

**★고장 주입으로 검증한 4가지**

| 케이스 | 결과 |
|---|---|
| 정상 job | ✅ 12초에 완료, `resultJson` 에 파일명 기록 |
| 없는 모델 지정 | ✅ `failed` 로 기록하고 **워커는 안 죽음** — 다음 job 이어서 처리 |
| `processing` 25분 박제 | ✅ **stale 회수**로 `pending` 복귀 후 재처리 |
| ComfyUI 재기동 중 job | ⚠️ **첫 시도에서 실패** → 아래 수정 |

★**ComfyUI 준비 대기(`wait_comfy`)를 추가한 이유**: 서버가 켜질 때 워커가 ComfyUI 보다
먼저 준비되면 첫 job 을 집어서 `Connection refused` 로 **실패 처리해버린다**(실측).
서버3 은 껐다 켜는 구조라 **매번 기동할 때마다 이 창이 생긴다** — 켤 때마다 첫 요청이
버려지는 셈이었다. systemd 의 `After=` 만으로는 부족하다(프로세스 시작 ≠ 서비스 준비).
→ 기동 시 대기 + job 을 집은 뒤에도 재확인, 미응답이면 **`failed` 가 아니라 `pending`
복귀**(ComfyUI 문제로 회원 요청을 버리면 안 된다).

★로그 확인 시 주의: 재시작했는데 **로그가 옛것 그대로**여서 "안 고쳐졌다"고 오판할 뻔했다.
줄 수·타임스탬프를 함께 봐야 새 로그인지 알 수 있다.

### 디스패처 (`rag/ai_studio_dispatcher.py`, 서버2 크론 `*/2`)

큐에 `pending` 이 있으면 서버3 을 자동으로 켠다. **끄는 것은 서버3 자신이 한다**
(`idle_shutdown.sh`) — 역할을 나눈 이유는 §5-4 참조.

```
큐에 pending 발생
   ↓ (서버2 크론 2분)
서버3 TERMINATED → gcloud instances start
   ↓ 부팅 ~1분, ComfyUI·gpu-worker 는 systemd 자동 기동
워커가 처리 → 일 없으면 서버3 이 스스로 종료(유휴 30분)
```

★**GCP 권한**: 기본 계정(`385781764140-compute@`)은 VM 액세스 스코프 제한으로 막혀 있다.
`aichat-vercel@...` 서비스 계정에 **Compute 인스턴스 관리자(v1)** 를 부여해 해결
(2026-08-05 사장 조치). 디스패처는 `--account=` 로 이 계정을 명시한다.

★**안전장치 3가지**
- **하루 기동 상한 12회** — 버그로 켜고 끄기가 반복되면 요금이 샌다. 상한 도달 시 1회 알림.
- **연속 실패 알림**(2·5·15회) — 조용히 안 켜지면 큐만 쌓이고 아무도 모른다.
  소음을 막으려 특정 횟수에서만 알린다.
- **flock** — 크론은 2분인데 기동은 더 걸린다. 중복 실행을 막는다.

★**큐가 비어도 서버를 끄지 않는다** — 사람이 웹에서 프롬프트를 짜는 중에도 큐는 비어 있다.
큐만 보고 끄면 작업 중인 사람을 끊어버린다. 끄는 판단은 서버3 이 유휴 시간까지 함께 본다.

★**전이 중 상태(STOPPING/STAGING)는 건드리지 않는다** — 중복 기동 방지.

**실전 검증(2026-08-05)**: 서버3 을 끈 뒤 큐에 job 적재 →
디스패처가 `TERMINATED` 감지 → 자동 기동(10초) → 부팅 후 ComfyUI·워커 자동 시작 →
**job 처리 완료(48초)**. 전 구간 사람 손 없이 동작 확인.
빈 큐(무동작)·서버 켜짐(중복 기동 안 함)도 각각 확인.

접힌 영역에서 확인할 수 있다 — **안 보이면 결과가 마음에 안 들 때 무엇을 고쳐야
할지 알 수 없다.**

품질 실측(2026-08-05): 입력 한 줄로 상업적으로 쓸 수 있는 인물 헤드샷·제품 컷 확인.

### 모델 관리

설치 5종: RealVisXL V5 / Juggernaut XL v9 / SDXL base / SDXL refiner / DreamShaper XL Turbo v2.
(디스크 193G 중 48G 사용, 모델 1개당 약 6.5GB)

★**임의 URL 은 받지 않는다.** `ai_studio_ctl.sh` 의 `MODEL_CATALOG` 화이트리스트에

### ★2단계에서 잡은 함정 (전부 실제로 겪음)

1. **`wget -q` 가 404 를 조용히 삼킴** — HuggingFace 는 없는 파일에도 404 를 주는데
   `-q` 라 로그가 없었다. 0바이트 `.part` 만 남아 "받는 중"으로 보였다.
   → `-nv` 로 로그를 남기고, 실패 시 `.part` 를 지운다.
   URL 은 반드시 HF API(`/api/models/<repo>`)로 실제 파일명을 확인하고 등록한다.
2. **`pgrep` 기반 BUSY 판정 실패** — wget 이 아직 안 뜬 순간을 놓쳐 2개가 동시에
   받아졌다. → `.part` **파일 존재**로 판정(파일은 즉시 생긴다).
3. **죽은 `.part` 가 영구 차단** — 서버가 받는 도중 꺼지면 `.part` 가 남고, 그걸
   BUSY 로 치면 이후 모든 다운로드가 영원히 막힌다.

4. **★유휴 자동종료가 다운로드를 죽였다** — `idle_shutdown.sh` 가 ComfyUI 큐만 보는데,

   → `.part` 가 있으면 "일하는 중"으로 본다. 수정 후 실측: `모델 내려받는 중 — 유지`.
5. **TDZ** — `pollDownload` 를 `load` 보다 뒤에 선언하면 최초 렌더 `useEffect` 에서
   초기화 전 접근으로 화면이 백지가 된다. **tsc 는 못 잡는다**(런타임 오류).
6. **★서버1 직접 수정 금지 규칙 위반** — 라우터를 서버1 작업본에 scp 로 직접 넣었다가
   원복했다. 정상 경로는 로컬 수정 → 커밋 → push → 서버1 `git pull` → `pm2 restart`.
   이때 **라우터 2개(`admin-ai-studio.ts`, `admin.ts` 마운트)가 커밋되지 않은 채
   서버1에만 있었다** — 서버 재구축 시 유실될 뻔했다. 정식 추적으로 전환.
7. **shared-api 포트는 3020** (3001 아님). pm2 는 `shared-api/node_modules/.bin/pm2`.

## 7-3. ★3단계: 실사 품질 개선 — FLUX 비교와 확대 후보정 (2026-08-05)

사장 질문 "미드저니급 실사를 만들려면 어떤 모델을 추가해야 되나?"에서 출발.

### ★결론부터: 모델이 아니라 후보정이 답이었다

같은 프롬프트·**같은 시드(8800)**·832×1216 으로 3장을 비교했다.

| 조건 | 결과 | 판정 |
|---|---|---|
| 1) RealVisXL V5, 35스텝 | 피부·머릿결 가장 자연스러움 | **채택** |
| 2) FLUX.1-schnell, 4스텝 | 매끈하나 인위적, **워터마크 흔적** 발생 | 기대 이하 |
| 3) FLUX + 2배 확대 | 해상도는 오르나 2)의 한계 그대로 | - |

★**"최신·상위 세대 모델 = 더 좋음"이 아니었다.** schnell 은 4스텝 고속 생성을 위해
세밀함을 포기한 버전이고, 그 대가가 컸다. 워터마크는 FLUX 가 학습 데이터의 스톡사진
워터마크를 재현하는 알려진 현상이다.

※ 이 제안은 Claude 가 "상업 이용 자유(Apache 2.0)"를 우선해 schnell 을 권한 것인데,
품질 대가를 과소평가한 판단이었다. 실측 결과를 그대로 보고하고 사장이 1)을 채택했다.

★**반면 확대 후보정의 효과는 분명했다** - 1024 원본은 피부·머리카락이 뭉개지는데,
4배 확대 후 2배로 줄이면 디테일이 살아난다(**축소가 핵심** - 키우기만 하면 흐려진다).
최종 확인: RealVisXL + 2배 확대 = **1664×2432, 58초, 워터마크 없음**, 1.4MB→5.9MB.

**→ 품질이 아쉬울 때 모델부터 바꾸기 전에 파이프라인에 빠진 단계(후보정·리파인)가
없는지 먼저 볼 것.** 업스케일 모델은 64MB에 불과한데 효과는 모델 교체보다 컸다.

### 적용

프리셋별 확대 후보정 기본값 - 디테일이 곧 품질인 것만 ON:

| 기본 ON | 기본 OFF |
|---|---|
| 프로필·패션·제품·인테리어·음식 | 썸네일·일러스트(작게 쓰거나 선이 단순) |

설치된 확대 모델이 없으면 옵션 자체를 숨긴다(켜도 소용없으므로).

### 설치 모델 (총 6종 + 확대 1종, 디스크 118G 여유)

RealVisXL V5 / Juggernaut XL v9 / SDXL base / SDXL refiner / DreamShaper XL Turbo v2 /
**FLUX.1-schnell fp8(17GB)** + **4x-UltraSharp.pth(64MB)**

★FLUX 는 채택되지 않았지만 **삭제하지 않고 보관**한다(나중에 dev 비교 여지).

**라이선스** - schnell = Apache 2.0(상업 자유) / dev = 비상업(내부 검토 전용).
본가 저장소는 gated(HF 토큰 필요)라 **Comfy-Org 재배포 fp8 단일본**을 쓴다.
fp8 단일 파일이라 VAE·텍스트인코더를 따로 받을 필요가 없다.

### ★FLUX 는 워커가 설정을 덮어쓴다

SDXL 설정을 그대로 주면 결과가 뭉개진다. `gpu_worker.py` 의 `_is_flux()` 분기:

어드민에서 FLUX 를 고르면 "설정이 자동 조정됩니다" 안내가 뜬다 -

## 7-4. ★4단계: img2img(원본 사진에서 바꾸기) (2026-08-05)

사장 질문 — "img2img가 왜 AI 스튜디오에 없지?"

### 왜 없었나 (빠뜨린 게 아니라, 만든 적이 없다)

파이프라인 **전 구간이 텍스트 전용**이었다. 한 군데를 고쳐서 될 일이 아니었다.

| 구간 | 원래 상태 |
|---|---|
| 워커 워크플로 | `EmptyLatentImage`(빈 노이즈) + `denoise: 1.0` **하드코딩** — 원본을 넣을 노드가 없음 |
| shared-api | payload 에 이미지 필드 없음 |
| 이미지 통로 | **단방향** — 서버3→어드민(`/image/:file`)만 있고 **올리는 경로가 없었다** |

### 무엇을 만들었나

1. **워커** — `init_image` 가 있으면 `LoadImage → ImageScale → VAEEncode` 로 latent 를
   만들어 KSampler 출발점을 바꾼다(`EmptyLatentImage` 는 그래프에서 제거).
2. **`ctl upload`** — 원본을 서버3 `ComfyUI/input/` 에 올린다.
3. **`POST /upload`** — 서버1이 base64 를 받아 ctl 로 중계.
4. **어드민 UI** — 원본 업로드 + **강도 슬라이더**(의미를 말로 표기).

### ★설계 판단 3가지 (되풀이하지 않기 위해)

- **원본을 DB에 넣지 않는다.** 사진 한 장이 수 MB라 `payloadJson` 에 넣으면 `GpuJob`
  테이블이 급격히 비대해지고 **목록 조회까지 같이 느려진다.** 원본은 파일, payload 는 파일명만.
- **base64 는 stdin 으로 넘긴다.** 명령줄 인자로 주면 수 MB 가 `ARG_MAX` 를 넘겨
  *"Argument list too long"* 으로 죽는다. 셸 인용 문제도 함께 사라진다.
- **브라우저에서 미리 축소해 올린다.** 화질을 버리는 게 아니다 — 워커가 **어차피
  생성 크기(최대 1216)로 리사이즈**하므로 4000px 를 올려도 1216 으로 줄여 쓴다.
  즉 큰 원본은 **업로드 시간만 늘고 결과는 같다.** (정교함은 출력 쪽 = 확대 후보정 담당)
  · 사장 제안이던 scp/구글드라이브 경유는 채택 안 함 — 원본은 **브라우저**에 있어
    첫 구간이 어차피 HTTP다. 드라이브는 서버3에 인증을 새로 심어야 해 관리 지점만 는다.

### ★denoise — img2img 결과를 좌우하는 값

| 값 | 의미 | 화면 표기 |
|---|---|---|
| 0.15~0.35 | 원본 유지, 화질·디테일만 정리 | 살짝 다듬기 |
| 0.45~0.65 | **구도·포즈 유지, 화풍 변경**(주력 구간) | 스타일 바꾸기 |
| 0.70~0.85 | 원본은 참고만 | 많이 바꾸기 |
| 0.90~ | 사실상 새 그림 | 완전히 새로 |

★**t2i 에서는 이 값을 무시한다** — 빈 노이즈에서 0.5로 출발하면 노이즈가 덜 지워져
**얼룩만 남는다.** 그래서 워커가 `init_image` 없으면 강제로 1.0 을 쓴다.

### 실측 검증 (2026-08-05, 서버3 실제 생성)

같은 원본·같은 프롬프트로 강도만 바꿔 원본과의 차이를 수치화:

| 조건 | 원본 대비 차이(작을수록 원본과 비슷) |
|---|---|
| denoise 0.25 | **12.8** |
| denoise 0.75 | **21.4** |
| t2i(원본 미사용) | **110.0** |

육안으로도 0.25는 원본과 거의 동일, 0.75는 **구도·색 배치는 지키면서** 다리·구름·
태양 광선이 새로 그려졌다. → **원본이 실제로 반영되고 슬라이더가 실제로 작동한다.**

### 곁들여 고친 것

- **모델명에 성격 표기**(`modelNote`) — 파일명만으론 인물용인지 사물용인지 알 수 없다.
  설치·카탈로그·생성 드롭다운 **3곳 공용**. 9종 전부 연결 확인.
- **"추가할 수 있는 모델"** 문구가 *"이게 무슨 얘기냐"* 는 오해를 샀다 →
  **"아직 설치되지 않은 모델 — 누르면 지금 내려받아 설치합니다"** 로 변경.
- **디스크 표시** — 모델 1개가 6.5GB고, 디스크 200GB 는 **서버를 꺼도** 월 2.8만원
  나가는 고정비다. 85% 이상이면 빨간색 경고. (실측 40%: 193GB 중 76GB, 모델이 48GB)
- **가독성** — 이 패널만 `text-gray-500/600` 을 **33곳** 썼다(다른 어드민 패널은 400/300).
  한 단계씩 밝히고 9~10px 글자도 2px 씩 키웠다. → Playwright 로 렌더해 눈으로 확인.
- **유휴 종료 시 원본 정리** — 안 지우면 사진이 계속 쌓인다(큐가 빈 상태라 안전).
- **다운로드 감지 버그** — `idle_shutdown.sh` 가 `checkpoints` 만 봐서 **업스케일 모델을
  받는 중엔 서버가 꺼질 수 있었다**(ctl 은 이미 양쪽을 봤다). `models/*/` 로 수정.

### 현황

- **동영상 모델은 없다** — 설치 7종·카탈로그 9종 전부 정지 이미지 전용.
  영상은 비용 성격이 다르다(편당 수백 원대) — 필요하면 별도 검토.

→ **LLM 프롬프트 재생성 없이도 상업용 수준**. 재생성 버튼은 **불필요**로 판단
(대신 한글 입력을 돕는 '다듬기' 버튼만 추가 — 아래).

### ★"전신 모델은 왜 없냐" — 이름 문제 + 진짜 문제

**이름 문제**: 없던 게 아니라 **'패션 화보'라는 이름이라 몰랐던 것**.
→ **'전신·패션'** 으로 개명. ★**이름이 용도를 못 드러내면 있어도 없는 것이다.**

**진짜 문제**: `head to toe`(머리부터 발끝)를 적었는데도 **발이 잘렸다**.
모델이 인물을 크게 잡으려는 성향 탓이다. 셋을 **같이** 걸어야 해결됐다:

1. `camera positioned far back with empty space above head and below feet` 명시
2. **네거티브에도** `close-up, headshot, upper body only, waist up, zoomed in` 추가
3. 렌즈 85mm → **50mm**(더 넓게)

→ 재생성 결과 **구두까지 완전한 전신** 확인. ★프롬프트 한쪽만으로는 잘 안 걸린다.

### ★스타일 참조(IP-Adapter) — img2img 와 다른 기능

사장 지적 — *"원본=참조 이미지를 올렸으면 대상 이미지를 올려서 원본처럼
만들어주는 거 아니냐?"* → **잘못 아신 게 아니라 다른 기능**이었다.

| | 입력 | 하는 일 |
|---|---|---|
| **내 사진 고치기**(img2img) | 사진 1장 | 그 사진 **자체를** 바꾼다 |
| **스타일 따라하기**(IP-Adapter) | 견본 1장 | 견본의 **화풍만 빌려** 새로 그린다(견본은 안 바뀜) |

★둘은 **같이도 쓸 수 있다**(내 사진을 고치되 견본 화풍으로).

**설치**: `custom_nodes/ComfyUI_IPAdapter_plus`(노드 35개) +
`ipadapter/ip-adapter-plus_sdxl_vit-h.safetensors`(808MB) +
`clip_vision/CLIP-ViT-H-14-laion2B-s32B-b79K.safetensors`(2.4GB)

**★워커 구현에서 놓치기 쉬운 것**: `KSampler` 의 `model` 입력을 **IPAdapter 출력으로
바꿔야** 효과가 난다. 노드만 추가하면 실행은 되는데 **결과에 아무 영향이 없다**
("적용했는데 그대로"의 전형적 원인). FLUX 에는 적용하지 않는다(SDXL 전용 구조).

**모드**(`style_mode`):
- `style transfer` — **화풍·색감만**(피사체는 프롬프트대로). 기본값
- `standard` — 인물·구성까지 폭넓게(**얼굴 비슷하게** 유지할 때)
- `prompt is more important` — 견본은 약하게

**실측 A/B**(같은 시드·같은 프롬프트, 견본=플랫 일러스트):
A(참조없음) = 실사 사무실 사진 / B(스타일참조) = **견본의 플랫 화풍·살구민트
팔레트로 그려진 같은 인물**. → 피사체는 프롬프트대로, 화풍만 견본에서 = **의도대로 동작**.

### ★잡은 버그 2개 (둘 다 실사용 중 터질 것들)

**1. ComfyUI 캐시로 "성공했는데 파일이 없다"**
로그 증거: `Prompt executed in 60.77s`(첫 생성) → 이후 `0.00 seconds` 3회.
ComfyUI 는 **완전히 같은 워크플로**를 다시 받으면 실행을 건너뛰고 **예전 결과의
파일명을 그대로 돌려준다**. 그 파일을 지웠다면 **DB 는 completed, 디스크엔 없음**.
→ 워커가 **결과 파일의 실제 존재를 확인**하고 없으면 실패로 올린다.

**2. 파일명 번호 재사용** (사장 지적: *"번호를 다시 쓰면 어떡하니"*)
`filename_prefix: "job"` 고정이라 ComfyUI 가 순번을 붙이는데, 삭제로 번호가 비면
**그 번호를 다시 쓴다**(실제로 `job_00029_` 가 두 번 쓰였다). 서로 다른 그림이 같은
이름을 갖고, 브라우저 캐시(1시간)에 남은 옛 그림이 계속 보인다.
→ **시각+난수 접두사**(`job_0805_162618_9263`). 이름이 안 겹치면 캐시를 오래 잡아도 안전.

### 성능·UX

- **보관함 썸네일 일괄** — 사장 *"삭제하고 불러오면 겁나 느리다"*.

- **프롬프트 보조** — 영어변환·LLM고급화 **두 버튼을 하나로 통합**(`✨ AI로 다듬기`).

  `↩ 되돌리기`(LLM 이 엉뚱하게 바꿔도 손으로 쓴 게 안 날아감), `📋 예시 넣기` 포함.
  API: `POST /refine-prompt`(gemini-2.5-flash) — ★**subject 한 줄만** 반환한다
  (촬영 용어는 프리셋 scaffold 담당. 여기서 또 쓰면 중복돼 프롬프트가 지저분해진다).
- **보관함 별도 탭** 분리, 모델명에 성격 표기, 디스크 사용량 표시,
  가독성 개선(이 패널만 어두운 회색 33곳·글자 9~10px 였다).

### ★성인용(NSFW) 모델 요청 — 진행하지 않음

기술 검토만 회신: 기존 구성은 깨지지 않으나(체크포인트는 파일 단위 독립),
**라이선스**(Pony·Illustrious 계열 상업이용 조건)·**결제/플랫폼 약관**이 실무 제약.
대안으로 화보·뷰티 톤 **품질 개선은 계속 지원** 가능하다고 안내.

## 7-6. ★6단계: 화면 오해 3건 정리 + 확대 유실 버그 (2026-08-06)

이날은 새 기능이 아니라 **"안 되는 줄 알았는데 실제로는 되고 있던 것"** 을 가려낸 날이다.
사장 지적 3건 중 **2건은 오해, 1건은 진짜 버그**였다. 셋 다 원인이 화면 문구에 있었다.

### ① "생성하기가 안 눌린다" — 프롬프트가 비어 있었다

`doGenerate` 첫 줄이 `if (!prompt.trim())` 으로 즉시 반환한다.
버튼은 멀쩡히 활성 상태인데 눌러도 아무 일이 없으니 "고장"으로 보인다.
→ 원인 안내만 하고 코드는 두었으나, **버튼 비활성화는 아직 미적용**(아래 남은 일).

### ② "스타일 따라하기로 전신이 안 나온다" — img2img 가 구도를 붙잡고 있었다

ComfyUI `/history` 에서 **실제 전송된 워크플로를 그대로 떠서** 확인했다(추측 금지).

```
job e9001134  (전신·패션 프리셋 사용)
  positive : "Full body editorial fashion photograph … entire body visible
              from head to shoes, camera positioned far back with empty space
              above head and below feet …"        ← 전신 문구 전부 도달함
  negative : "… close-up, headshot, upper body only, waist up, zoomed in"
  denoise  : 0.55          ← ★범인
  latent   : ["15", 0]     ← 원본 인코딩에서 출발(빈 노이즈 아님)
  ImageScale: 832×1216, crop "center"
```

**프롬프트는 결백했다.** 원인은 두 가지다.

1. **denoise 0.55 는 구도를 못 바꾼다.** 구도·인물 배치 같은 큰 구조는 초기 스텝에서
   정해지는데, 0.55 면 그 출발점이 이미 원본(상반신 클로즈업)으로 고정돼 있다.
   프롬프트에 `entire body` 를 아무리 넣어도 이미 정해진 배치를 뒤집을 힘이 없다.
2. **`crop: "center"` 가 다리를 잘라낸다.** 상체 사진을 832×1216 에 중앙 크롭으로
   맞추므로, 전신 정보는 애초에 입력에도 없다.
   ★**단 이 항목은 뒤에 실측으로 과대평가로 판명됐다**(같은 날, §7-6 남은 일 ③ 참조) —
     불리하게 작용하지만 **결정적이지 않다.** `denoise` 를 0.85 로 올리면 crop 으로도
     전신이 나온다. 여백 패딩은 오히려 결과를 나쁘게 만들어 채택하지 않았다.

→ **정답은 "내 사진을 빼는 것"**이다. 원본을 빼면 `latent` 가 빈 노이즈로 돌아가고
  denoise 가 1.0 이 되어 프롬프트의 전신 지시어가 온전히 작동한다. 견본만 남기면
  화풍은 유지된다. "내 얼굴 유지 + 전신"은 img2img 로는 원리상 양립이 어렵다.

★같은 조회에서 **프롬프트가 통째로 빈 잡**(`"An image, imitating a style"`)도 나왔다 —
 프리셋 없이 돌린 건. 화면만 봐선 구분이 안 되니 실제 전송값을 봐야 한다.

### ③ ★진짜 버그 — 서버가 꺼져 있으면 「선명하게」가 영영 꺼진다

```ts
setUseUpscale(!!p.upscale && upscalers.length > 0);
```

`upscalers` 는 **서버가 RUNNING 일 때만** 채워진다. 그 전에 프리셋을 고르면
조건이 false 라 체크가 안 켜지는데, **나중에 목록이 도착해도 다시 켜주지 않았다.**
사장은 켜진 줄 알고 쓰는데 실제로는 확대 없이 생성돼 **조용히 품질만 떨어진다.**

→ 프리셋의 확대 **의도**(`wantUpscale`)를 체크 상태와 분리해 기억해 두고,
  `upscalers` 가 **`없음 → 있음` 으로 바뀌는 그 순간에만** 반영한다.

- ★매번 반영하면 사장이 직접 끈 체크를 15초 주기 갱신이 도로 켜서
  **'끌 수 없는 체크박스'** 가 된다. 전이 시점 한정이 핵심.
- ★프리셋 해제(직접 입력) 시 의도도 함께 지운다 — 안 지우면 옛 의도가 남아
  목록 도착 시 체크가 되살아난다.

**실측 5종 전부 통과**(상태머신을 코드 그대로 옮겨 실행):

| 시나리오 | 결과 |
|---|---|
| 서버꺼짐 → 프리셋 → 서버켜짐 | ✅ 뒤늦게 ON (수정 확인) |
| 서버켠 뒤 프리셋(정상경로) | ✅ ON 유지 (회귀 없음) |
| 직접 체크를 끔 → 갱신 반복 | ✅ OFF 유지 (도로 안 켜짐) |
| 썸네일(확대 미사용) 프리셋 | ✅ OFF |
| 프리셋 해제 → 서버켜짐 | ✅ 되살아나지 않음 |

### ★프리셋 자동반영 자체는 정상이었다

"위 선택에 따라 자동으로 안 바뀐다"는 지적을 받고 7종을 전수 검증했으나
**모델·크기·스텝 전부 정상 반영**됐다. 문제의 화면(`DreamShaperXL_Turbo_v2`
+ 스텝 30 + 확대 OFF)은 **프리셋 미선택 상태**였다 — 서버가 준 모델 목록의
**첫 번째**가 DreamShaper 라 자동 선택된 기본값이고, 시뮬레이션에서 세 값이
모두 일치해 확정했다. 프리셋 버튼의 보라색 강조가 없던 것도 방증.

### 모델 설명 — '성격'이 아니라 '용도'를 앞에

사장 지적: "설명이 더 헷갈려."
`'실사 인물 최고 — 프로필·헤드샷'` 처럼 **성격**만 적으니 *그래서 내가 뭘 골라야
하는지*가 안 보였다. **용도(언제 쓰는지)를 앞**에 두고 금지 대상은 못박는다.

| 이전 | 지금 |
|---|---|
| 실사 인물 최고 — 프로필·헤드샷 | ★사람 사진은 이걸로 — 얼굴·피부가 가장 자연스러움 |
| 사물·공간에 강함 | ★물건·공간은 이걸로 — 제품컷·인테리어·음식 |
| 기본 모델 — 무난하지만 밋밋함 | 특별히 잘하는 게 없음 — 위 둘을 먼저 쓰세요 |
| 보정 전용 — 단독 생성용 아님 | ⛔이걸로는 그림이 안 나옴 — 고르지 마세요 |
| 고품질이나 ★비상업 | ⛔판매용 금지(비상업 전용) — 내부 검토만 |

기호는 **★=권장 / ⛔=고르지 말 것** 둘만 쓴다.

★**`<option>` 안에서는 줄바꿈·색상이 브라우저에서 무시**되고, 닫힌 select 는 폭이
좁아 괄호 설명이 잘린다. 그래서 드롭다운을 카드로 바꾸는 대신 **아래에 설명을 다시**
띄웠다(★=초록 / ⛔=빨강). 모델 관리 목록도 같은 색 규칙으로 통일.

### 남은 일 3건 처리 — 그중 하나는 실측이 가설을 뒤집었다 (같은 날 이어서)

**① 프롬프트가 비면 생성 버튼을 잠근다** ✅
`disabled={busy || !prompt.trim()}` + 문구 `⌨ 먼저 프롬프트를 입력하세요`.

**② FLUX + 견본 경고** ✅
워커가 `if style_image and not flux` 로 조용히 건너뛴다(IP-Adapter 가 SDXL 전용).
FLUX 와 견본이 **동시일 때만** 경고를 띄우고 SDXL 모델로 바꾸라고 안내한다.

**③ ★여백 패딩 — 구현했다가 실측 후 되돌림**

가설은 위 §②에 쓴 대로 *"`crop:center` 가 다리를 잘라 전신이 원리상 불가능하다"* 였다.
서버3을 켜 `ResizeAndPadImage` 설치를 확인하고(`/object_info`, IMAGE 출력) 구현한 뒤,
**같은 프롬프트·같은 시드로 4장을 비교**했다.

| 조합 | 결과 |
|---|---|
| denoise 0.85 + **crop** | ✅ **전신 정상**, 배경도 깨끗 ← 제일 낫다 |
| denoise 0.85 + **pad** | ⚠️ 전신은 나오나 **흰 띠가 남고** 여백이 **검은 아치 물체로 변형** |
| denoise 0.55 + **crop** | ❌ 상반신 그대로 |
| denoise 0.55 + **pad** | ❌ 상반신 + 위아래 **흰 띠만 추가** |

★**가설이 틀렸다.** 모델이 **여백을 배경 오브젝트로 읽어버려** pad 가 오히려 나빴다.
그리고 **전신을 가르는 진짜 변수는 crop/pad 가 아니라 `denoise`** 였다 —
0.85 로 올리면 **crop 으로도 전신이 잘 나온다.**

→ 워커·API·UI 의 `fit` 분기를 **전부 되돌렸다**(서버3 재배포, md5 일치 확인).
  옵션을 늘리는 대신 **강도 0.85 안내**를 강도 슬라이더 옆에 띄운다(0.8 미만일 때만 표시).

★위 §② "crop 이 다리를 잘라 전신이 불가능하다"는 서술은 **과했다.** crop 은 불리하게
 작용하지만 **결정적이지 않다** — denoise 가 낮은 것이 주된 원인이었다.

### ★확대 모델 2종 A/B — UltraSharp 우위 확정 (2026-08-06)

사장 요청("RealESRGAN 써보고 설명 달아줘")으로 확인해 보니 **카탈로그에만 있고 설치는
안 돼 있었다.** 서버3을 켜 받아서(64MB) 같은 시드·같은 프롬프트로 3장을 돌리고,
얼굴 부위를 **원본 픽셀 그대로 잘라** 대조했다.

| | 결과 |
|---|---|
| 확대 없음 | 피부결·잔머리가 뭉개져 흐릿 |
| **4x-UltraSharp** | 속눈썹·잔머리가 **한 올씩** 살고 모공까지 보임 ← **확실한 우위** |
| RealESRGAN_x4 | 매끈하지만 **피부 질감을 뭉개** 플라스틱처럼 됨(확대 없음보다 인위적) |

속도는 둘 다 **10초로 동일**. "부드럽게 확대"라는 성격 자체는 맞지만,
**인물 사진에서는 그 부드러움이 곧 단점**이다.

★**단 이 결론은 아래 2차 실측에서 절반이 뒤집혔다** — 인물만 보고 "비추천"이라
 단정했으나, **소재가 갈리는 문제**였다. 바로 다음 항목을 볼 것.

### ★확대 모델 2차 A/B — 1차 결론 정정: 우열이 아니라 **소재**다 (2026-08-06)

*"인물이 아닌 소재로 한번 더 테스트해봐"* 지시로 플랫 일러스트·제품컷을 같은 시드로 비교했다.

| 소재 | 나은 쪽 | 진 쪽의 증상 |
|---|---|---|
| 인물 사진 | **UltraSharp** | RealESRGAN 이 피부를 뭉개 플라스틱처럼 |
| 제품 컷(광택) | **UltraSharp** | RealESRGAN 이 반사광을 뭉개 밋밋해짐 |
| **플랫 일러스트** | **RealESRGAN** | UltraSharp 가 평면에 **자글자글한 노이즈**를 만듦 |

★핵심: 같은 **"선명하게 하는 힘"이 사진에선 디테일로, 평면 그림에선 노이즈로** 나타난다.
 **"인물에서 졌으니 나쁜 모델"이 아니었다.**

★속도도 1차와 달랐다 — 1차(인물)는 둘 다 10초였는데, 2차 재측정은
 **UltraSharp 60초 / RealESRGAN 10초**. 평면 그림에선 RealESRGAN 이 품질·속도 모두 낫다.

→ 설명을 **우열이 아니라 소재 기준**으로 교체:
  `★사진(인물·제품)은 이걸로 — 머리카락·광택이 또렷해집니다(기본)` /
  `일러스트·평면 그림에 좋음 — 사진에 쓰면 질감이 뭉개집니다`
→ `pickUpscaler(list, flat)` 이 **소재에 맞춰** 고른다(일러스트·썸네일 프리셋이면 평면).
  설치 안 된 쪽이면 조용히 차선으로 떨어진다(없는 모델명을 보내면 생성이 실패한다).
  선택로직 9종 검증(사진/평면 × 역순·단독설치·미지·0개).

**★곁들여 잡은 것 — `upscalers[0]` 은 설치 순서에 결과가 좌우된다**
어느 확대 모델을 쓸지 고르는 칸이 없는데 코드는 **목록 첫 번째**를 쓰고 있었다.
지금은 정렬상 UltraSharp 가 먼저라 우연히 맞았을 뿐, RealESRGAN 이 먼저 오면
**더 나쁜 쪽으로 조용히 바뀐다.** → `pickUpscaler()` 로 **이름을 보고 UltraSharp 우선**.
우열이 분명하므로 고르는 칸은 만들지 않고, 대신 체크박스에
`좋은 쪽(4x-UltraSharp)으로 자동 적용됩니다`라고 **무엇이 쓰이는지 밝힌다.**
(선택로직 5종 검증: 역순·단독설치·미지모델·0개 포함)

※ RealESRGAN 은 **보관 결정이 옳았다**(64MB) — 2차 실측에서 **플랫 일러스트 전용으로
 쓸 자리가 확인**됐다. 1차만 보고 지웠으면 그 용도를 영영 몰랐을 것이다.

## 🖼 3단계 — 서비스 연동 실적 (2026-08-07)

기획 당시 "3단계: 서비스 연동"으로 잡아둔 항목의 실제 착수·완료 기록.
**★API를 버리지 않는다**는 원칙(GPU 기본, API 폴백)을 전 구간에서 지켰다.

### 판별 기준 — "참조 사진을 넣는가" 하나

전환 가능 여부는 **`inline_data`(파이썬)·`inlineData`(TS) 유무**로 갈린다.
넣으면 불가(얼굴 보존), 안 넣으면 가능(순수 텍스트→이미지).

| 구분 | 기능 | 위치 |
|---|---|---|
| ✅ 적용 | 쇼츠(참조사진 없는 장면) | `rag/shorts_maker_worker.py` `_regenerate_scene` src_bytes=None |
| ✅ 적용 | 홈페이지 이미지 | `rag/homepage_worker.py` `generate_images` |
| ✅ 적용 | 쇼츠 카드 배경 | `shared-api/routes/aimp/admin-shorts.ts` `genCardBgImage` |
| ✅ 적용 | 전자책 삽화 | `shared-api/lib/gemini.ts` `generateEbookImage` |
| 🔴 불가 | 헤어스타일·시간여행·프로필사진 | `shared-api/lib/gemini.ts` (원본 사진 참조) |
| 🔴 불가 | 홈페이지 **편집** | `rag/homepage_edit_worker.py` (기존 이미지 참조) |
| ⚠️ 제외 | 전자책 **표지** | `gpt-image-2` — 제목 **한글 렌더링**이 필요해 SDXL로 대체 불가 |

얼굴 보존 4곳은 InstantID/IPAdapter FaceID 구축이 선행돼야 한다(서버3에 전무).
상세 조건은 메모리 `project_todo`의 "프로필사진 서버3 전환" 항목.

### 공용 모듈

- `rag/gpu_image.py` (파이썬) / `shared-api/lib/gpuImage.ts` (TS)
- 흐름: `GpuJob` 큐 적재 → 완료 폴링 → 결과 바이트 회수
- **서버3을 직접 호출하지 않는다** — 큐에 넣으면 `ai_studio_dispatcher`(서버2 크론 */2)가
  꺼져 있는 서버3을 켜고 워커가 처리한다. 서버3은 유휴 30분에 스스로 끈다.
- 실패는 조용히 `None`/`null` → 호출부가 gemini 폴백
- 스위치: `SHORTS_GPU_TEXT2IMG` / `HOMEPAGE_GPU_TEXT2IMG` / `SHORTS_CARDBG_GPU` / `EBOOK_IMAGE_GPU` (=0이면 끔)
- ★**seed를 항상 명시한다** — 워커는 seed가 없으면 초 단위 시각으로 채워서,
  한 건에서 여러 장을 연속 적재하면 **같은 초에 걸려 똑같은 그림**이 나온다.

### ★비용보다 컸던 이득 — 쿼터 대기 제거

홈페이지는 API 경로에서 나노바나나 쿼터 회복을 위해 장마다 `IMAGE_GAP_S = 25`초를 쉰다.
4장이면 **순수 대기만 100초**였고, 회원이 결과를 기다리는 기능이라 체감이 컸다.
GPU는 우리 서버라 쿼터가 없어 이 텀이 필요 없다.

★텀 계산은 `i > 0`이 아니라 **`api_calls > 0`**으로 세야 한다 —
`i`로 세면 GPU가 다 처리한 뒤 폴백 1장에도 불필요하게 25초를 쉰다.

### ★에러 없이 틀리는 실패 2건 (둘 다 눈으로만 잡힌다)

**① 한글 프롬프트를 SDXL에 그대로 보냄**
카드 배경에 "생일 케이크와 풍선이 있는 파티 테이블"을 한국어로 보냈더니
**전혀 무관한 인물 클로즈업**이 나왔다. SDXL은 영어로 학습된 모델이라 한글을 무시하고
학습 데이터의 흔한 구도를 그린다.
★위험한 건 **에러가 안 난다**는 점 — 반환값·크기(1.23MB)·소요시간(22초)이 전부 정상이라
로그엔 `GPU 생성 성공 — 1229406B`로 찍힌다. **눈으로 보기 전엔 성공한 줄 안다.**

→ `toEnglishPrompt()`(gemini-2.5-flash)가 **GPU로 보낼 때만** 영어로 번역한다.
화면 표시·회원이 ChatGPT에 복사하는 프롬프트는 **한글이어야 하므로**(2026-07-25 사장 지시)
원본은 바꾸지 않는다. 번역 결과에 한글이 남으면 실패로 보고 API 폴백(반쪽 번역이면 같은 사고).

**② 일러스트를 지시했는데 사진이 나옴**
전자책 삽화가 "깔끔한 플랫 일러스트" 지시에도 사실적인 사진으로 나왔다.

**원하는 스타일을 코드가 스스로 막고 있었다**(4곳 전부 기본값 하나로 보낸 탓).

→ 용도별 상수 분리. 2026-08-05 A/B로 이미 정리돼 있던 기준을 그대로 쓴다:

| 모델 | 용도 |
