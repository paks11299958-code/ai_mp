# 사이트·인프라 감시 (3시간 상태보고)

> `ai_mp/monitor.js` — **서버2** crontab `0 */3 * * *`. 결과를 텔레그램으로 발송하고
> `monitor-status.json`에 기록(어드민 '서버 모니터' 탭이 이 파일을 읽는다).
> 별개로 `rag/alert_monitor.py`(서버2, 10분 주기)가 자원·PM2 임계 감시를 담당한다.

## 왜 있나 — "알림이 없다"가 "정상이다"를 뜻하게 만들기

이 감시의 존재 이유는 **조용히 멎는 것을 잡는 것**이다. 실제 사고들이 전부 그랬다:

| 사고 | 그때 사이트는 |
|---|---|
| 토스봇 일손실 한도 HALT, 알림 0건 (07-31) | HTTP 200 정상 |
| 헤르메스 OOM 사망 → 텔레그램 무응답 (07-29·30) | HTTP 200 정상 |
| 서버2 스왑 고갈로 크론 통째 동결 (07-30) | HTTP 200 정상 |

★2026-07-31까지는 알림 경로가 **Brevo 이메일**이었는데, 서버 IP 미등록으로 401이 나
**점검은 정상 동작했지만 결과가 전달되지 않고 있었다.** 텔레그램으로 교체(IP 화이트리스트
없음 = 서버 IP가 바뀌어도 동작).

종전엔 **사이트 열림·로그인 2개**만 봤다. 정작 멎던 것들이 전부 그 바깥이라 확장했다.

## 설계 원칙 (★함정과 함께)

- **정상일 때도 전체 요약 발송**(사장 결정). 알림이 안 오는 게 정상인지 감시가 죽은
  건지 구분 못 하면 감시가 아니다. 정상 항목도 값을 실어 보낸다(halt 여부·발굴 기준일·
  자원 수치가 여기 있다).
- **스크린샷은 웹(site/login) 장애일 때만** 첨부. DB 이상에 사이트 화면은 단서가 없고,
  정상 보고까지 이미지면 알림이 무거워져 정작 장애를 흘려보게 된다.
- `status.json`의 `ok`는 **site+login 의미를 유지**(어드민 대시보드가 쓰는 값).
  전체 판정은 `allOk`로 분리 — 토스봇 halt 같은 다른 축의 이상을 섞으면 화면 의미가
  조용히 바뀐다.
- ★**`pgrep -f <이름>`은 쓰지 않는다** — 패턴이 **자기 명령줄에도 매칭**돼(셸·grep·
  백업 스크립트가 그 문자열을 달고 있으면) 대상이 죽어도 "살아있다"고 오판한다.
  실측: 존재하지 않는 이름을 넣었는데 3건이 검출됐다. `ps -eo pid=,args=`로 교체.
- ★**DB 계정이 컨테이너마다 다르다** — `n8n-docker-db-1`(aichat·company_wiki·n8n_db 등
  6개 DB)는 `aichat_user`, `n8n-docker-typebot-db-1`은 `postgres`. 컨테이너 기본값
  `POSTGRES_USER`로는 aichat에 못 붙는다. **운영이 실제 쓰는 계정**(shared-api
  DATABASE_URL)으로 붙어야 권한까지 함께 검증된다.
- ★**PostgreSQL 컨테이너는 2개다.** 하나만 보면 타입봇 DB가 죽어도 "DB 정상"이 된다.
- ★**3xx를 실패로 세지 않는다** — 타입봇 빌더는 비로그인 접근에 **307로 `/signin`**
  보내는 게 정상 동작(실측). 4xx/5xx만 장애로 센다.
- ★**pg_isready만 보면 안 된다** — 준비됐다고 답하면서 실제 질의는 실패하는 구간이
  있다(work_lessons). 실제 SELECT를 던져 응답까지 확인한다.
- **node fetch는 IPv6 폴백을 못 한다** — 이 서버는 IPv6 경로가 막혔는데
  `api.telegram.org`는 AAAA를 준다. curl은 IPv4로 폴백하지만 node fetch는 ETIMEDOUT.
  `undici` Agent `connect: { family: 4 }`로 IPv4 강제(`dns.setDefaultResultOrder`로는
  안 잡힌다).
- 텔레그램 발송 실패가 **점검 결과 기록을 막지 않는다** — 던지지 않고 false 반환.
  (예전 Brevo판은 여기서 throw해 크론이 통째로 죽었다.)

## ★감시자 자신이 차단될 수 있다 (2026-08-05)

배포 확인차 사이트를 반복 호출하다 **서버2 IP가 Vercel 봇 차단(403 Security
Checkpoint)** 에 걸렸다. 같은 시각 서버1에서는 HTTP 200 — **사이트는 정상인데 감시하는
쪽만 막힌** 상태다.

종전 코드는 403을 그대로 장애로 보고했다. 그러면 ①"사이트가 죽었다"는 거짓 경보가 나가고
②`site.ok=false`라 로그인 점검까지 통째로 스킵된다. 거짓 경보가 반복되면 진짜 장애
알림을 흘려보게 된다.

→ 403 + 본문에 `Security Checkpoint`면 **감시 IP 차단**으로 판정하고 문구에
"사이트 자체 장애가 아닐 수 있으니 다른 경로에서 확인"을 명시한다.
`ok=false`는 **유지** — 조용히 통과시키면 진짜 403 장애를 놓친다. 사람이 판단할 수 있게
'무엇이 일어났는지'를 정확히 적는 쪽을 택했다.

자원이 말라 개별 작업만 죽는' 구간**이다(07-30 스왑 고갈이 정확히 그 구간).
07-29 사고 때는 스왑 감시가 **자기도 얼어붙어** 22:10·22:20 실행이 통째로 누락된 채

## ★무료 한도가 있는 서비스는 "금액"으로 감시하면 영영 안 보인다 (2026-08-08)

사장 질문 "우리 사이트 음성서비스 비용이 발생되고 있는지 확인해봐"에서 드러난 사각지대.

**음성(Google Cloud TTS, Chirp3-HD)은 월 100만자가 무료**다. 그래서 한도 안에서는
**청구가 0원**이고, 비용 대시보드에도 일일 USD 임계 알림(`ai_cost_guard.py`, 기본 $1)에도
**절대 안 걸린다** — 넘는 순간 조용히 과금이 시작된다.

### 두 겹으로 대응

1. **어드민 [시스템 → 서버 모니터]** 최상단 카드에 **금액이 아니라 소진률(%)**을 표시.
   솔라피=잔액, OpenAI=누적액인데 TTS만 성격이 다르기 때문. 80% 경고 / 100% 초과 경고.
   집계는 **달력 월(KST)** 기준 — 무료한도가 월 리셋이라 "최근 30일"이면 소진률이 틀린다.
2. **`ai_cost_guard.py`에 `check_tts()` 추가** — 판정은 '현재 소진률'이 아니라
   **월말 예상 소진률**(`실제 ÷ (경과일 ÷ 그달 총일수)`)이 주다.
   ★**8/29의 80%는 정상**(며칠 뒤 리셋)이지만 **8/10의 80%는 큰일**이라, 같은 값도 뜻이 다르다.
   여기에 **실제 80%**를 OR 안전망으로 둔다(사장 선택 B안) — 월말에 페이스가 갑자기 튀면
   예상치가 늦게 반응하므로, 놓치는 것보다 한 번 더 알리는 쪽이 낫다.
   알림엔 **경로별 문자수**(뉴스/쇼츠/수학)를 붙여 **뭘 줄일지 즉시 판단**하게 했다.

### ★"기록 코드를 넣었다" ≠ "기록되고 있다"

이 작업의 진짜 발견은 감시 설계가 아니라 **기존 로깅이 3주간 죽어 있었다**는 것이다.
- `AiUsageLog`에 `google-tts` 행이 **0건**이었다(쇼츠 16건을 만드는 동안).
- 원인은 INSERT의 **파라미터 번호가 밀린 것**: `VALUES ($1,$2,$3,$4, 0, $4, $5, $6, NOW())`처럼
  `$4`를 두 칸에 재사용해 놓고 뒤를 이어붙여, **자리표 개수와 값 개수가 우연히 맞아** 멀쩡해 보였다.
- ★발각이 늦은 진짜 이유는 문법이 아니라 **구조**다 — `catch`가 조용히 삼키고 호출부가
  `void`(fire-and-forget)라 **화면·응답·로그 어디에도 신호가 0**이었다.
  심지어 그 파일 주석엔 "비용 사각지대라 추적한다"는 취지가 적혀 있었다: **의도는 기록됐는데 동작은 죽어 있었다.**
- ★게다가 **경로가 하나가 아니었다** — 뉴스는 `agent-api/news_collector.py`가 Google TTS를
  **직접** 호출해 `math-tutor-tts.ts`를 안 거친다. 하필 **최대 소비처**(월 약 40만자)라
  그것만 고쳤으면 계속 못 봤을 것이다. 공통 함수를 고치기 전 **외부 API 심볼로 전수 grep**할 것.

**교훈**: 감시·계측 코드는 **성공 경로가 조용하다**. 넣은 직후 한 번은 대상 테이블을 직접 조회해
행이 쌓이는지 확인해야 한다.

## ★감시 서버 IP가 차단되면 "사이트 장애"처럼 보인다 — 교차확인으로 구분 (2026-08-11)

Stop 훅이 `site: 403 / login: 건너뜀`으로 두 번(08-09·08-11) 경고했는데, **매번 서버1에서는
HTTP 200 정상**이었다. 사이트가 아니라 **감시 서버(서버2) IP가 Vercel 보안 체크포인트에 걸린 것** —
배포 검증하며 운영 사이트에 Playwright로 20회 넘게 접속한 결과였다.
**회원은 각자 다른 IP**로 들어오고 실제 브라우저는 체크포인트를 자동 통과하므로 **영향이 없다.**

원래도 403+`Security Checkpoint`를 **인식은** 하고 있었지만 `ok:false`로 두어 결국 실패로 보고됐고,
★상태 파일이 3시간 크론 산출물이라 **차단이 해소된 뒤에도 최대 3시간 같은 알림이 반복**됐다.

**조치** — 사람이 하던 판별(다른 IP에서 확인)을 그대로 자동화했다.
- 체크포인트 감지 시 **서버1에서 `curl`로 교차확인** → 200이면 `ok:true`로 통과시키되
  detail에 "감시 IP만 차단, 사이트 정상"을 남긴다(조용히 묻히지 않게).
- ★**서버1도 실패하면 `ok:false` 유지** — 헛알림을 줄이는 것보다 **진짜 장애를 놓치지 않는 게 우선**이다.
- `login`도 같은 경우 "차단으로 점검 생략"으로 통과 — site는 정상인데 login만 빨간 헛알림이 남던 문제.

**검증(3경우 전부 실측)**: ①정상 → 회귀 없음 ②차단 재현(`page.route`로 403+체크포인트 본문 주입)
→ `allOk:true` ③진짜 장애(서버1 교차확인도 실패로 강제) → `allOk:false`.
★시뮬은 운영 코드를 고치지 않고 **별도 파일+별도 상태파일**로 돌렸다.

**예방**: 배포 확인은 `vercel_status.sh`(REST API)를 먼저 쓰고, 브라우저 검증은 **간격을 두고 최소 횟수**로,
화면 검증은 가능하면 **로컬 프리뷰**에서 끝낸다.
