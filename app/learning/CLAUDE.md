# CLAUDE.md — 개발 지침

## 프로젝트

기존 **AI 데이터(aichat.dbzone.kr)** 프로젝트에 **AI 학습코칭** 기능을 추가한다.
이 하위 디렉토리 작업 시 `PRD.md`가 **유일한 기준**이다. 이 문서는 개발 방식만 규정한다.
두 문서가 충돌하면 `PRD.md`를 따른다.

---

## 가장 먼저 할 일

1. 프로젝트 루트의 `Work_index.md`를 읽는다. 서버 환경, 계정 구조, DB 구성이 정리되어 있다.
2. `PRD.md` 0장의 확인 사항 중 `Work_index.md`에 없는 항목만 코드베이스에서 직접 확인한다.
3. 필요한 내용(프레임워크, 인증 방식, 사용자 테이블명과 PK, 페르소나 목록 위치, 디자인 시스템)을 요약해 보고한다.
4. `PROGRESS.md`가 이미 있으면 읽고 이어서 진행한다. 없으면 새로 만든다.

**추측으로 진행하지 않는다.** 특히 인증과 사용자 테이블 구조는 반드시 실제 코드를 확인한 뒤 결정한다.

---

## 작업 모드

- 자율 개발 모드로 진행한다. 단계마다 승인을 요청하지 않는다.
- 오류가 나면 스스로 원인을 찾아 수정하고 다시 테스트한다.
- `PRD.md` 13장 완료 조건을 **전부** 충족할 때까지 계속 작업한다.
- 명백히 진행이 불가능할 때만 멈추고, 무엇이 왜 막혔는지와 시도한 방법을 보고한다.

### 반드시 사용자에게 확인할 것

- 환경 변수 값 (DB 접속 정보, API 키)
- 기존 코드나 기존 테이블을 **수정해야만** 하는 경우
- 프로덕션 DB에 대한 마이그레이션 실행
- `PRD.md`에 없는데 방향을 바꾸는 판단
- 되돌릴 수 없는 작업

## 세션 연속성 규칙

컨텍스트 한도나 사용량 한도 때문에 작업이 중단될 수 있다. **중단되어도 다음 세션이 이어받을 수 있는 상태를 항상 유지한다.**

### 작업 묶음

개발 작업 12단계를 한 번에 처리하지 않는다. 아래 묶음 단위로 진행하고, 한 묶음이 끝나면 보고하고 멈춘다.

- **묶음 A**: 1~2단계 (조사 + 마이그레이션)
- **묶음 B**: 3~5단계 (카드·랜딩·온보딩·커리큘럼)
- **묶음 C**: 6~8단계 (대시보드·학습·퀴즈·간격 반복·오답 노트)
- **묶음 D**: 9~10단계 (Cron·알림·리포트)
- **묶음 E**: 11~12단계 (반응형·테스트·완료 검증)

사용자가 특정 묶음을 지정하면 그 묶음만 수행한다.

### PROGRESS.md 갱신

각 단계를 마칠 때마다 루트의 `PROGRESS.md`를 갱신한다. 형식은 다음과 같다.

```markdown
# 진행 상황

## 완료
- [x] 1. 코드베이스 조사 → 확인 결과: (프레임워크/인증/사용자 테이블명 등)
- [x] 2. 마이그레이션 작성 → 파일: migrations/0001_learning.sql (미실행)

## 진행 중
- [ ] 3. 페르소나 카드 추가 → 남은 작업: ...

## 다음 할 일
- 4. 온보딩

## 결정 사항
- ORM: Drizzle 사용 (기존 프로젝트에 ORM 없음)
- 사용자 테이블: users.id 참조

## 막힌 것 / 사용자 확인 필요
- (없음)
```

**규칙**
- 완료 항목에는 결과와 파일 경로를 함께 적는다. "완료"만 적지 않는다
- 스스로 내린 기술 결정은 반드시 "결정 사항"에 남긴다. 다음 세션이 같은 결정을 다시 하지 않도록
- 컨텍스트가 압축되었다고 판단되면 `CLAUDE.md`, `PRD.md`, `PROGRESS.md`를 다시 읽고 진행한다

### 중단 대비

- 작업 중 하나가 걸릴 것 같으면 **손을 대다 버리지 말고** 현재 파일을 마무리한 뒤 커밋하고 `PROGRESS.md`를 갱신한다
- 빌드가 깨진 채로 세션을 끝내지 않는다

## Git 규칙

- 항상 `feature/learning-coach` 브랜치에서만 한다. `main`을 직접 커밋하지 않는다
- 마이그레이션은 **파일로만 작성한다. 프로덕션 DB에 직접 실행하지 않는다.** 실행은 사용자가 확인 후 수행한다
- 개발용 DB는 스키마가 지정되어 있으면 그곳에서만 검증한다

## 서버 구성

| 서버 | 내부 IP | 역할 |
|---|---|---|
| 서버1 | 10.178.0.2 | **운영** — Nginx, PostgreSQL(`aichat`, 정본), `shared-api`(Express, pm2 상시 구동) |
| 서버2 | 10.178.0.3 | **개발** — 이 세션이 도는 곳, cron 워커(`rag-env` venv), agent-api(8000) |
| 서버3 | 10.178.0.5 | 온디맨드 GPU (평소 꺼짐, 이 프로젝트와 무관) |

- 백엔드 로직은 **서버1의 `shared-api`**
- DB 정본은 **서버1의 PostgreSQL(`aichat`)**
- 정기 작업은 **서버2 crontab** → 서버1 `shared-api` 엔드포인트를 HTTP로 호출

**작업은 서버2에서 하지만 코드와 DB의 실체는 서버1에 있다.** 이 분리를 항상 의식한다.

## 배포 및 실행 순서

### ★이 프로젝트는 자동배포 구조다 — main/master 머지가 곧 운영 배포다(2026-08-11 확정)

- **shared-api**: 서버1 crontab이 1분마다 `origin/main`을 확인해, 새 커밋이 있으면 자동으로
  `git pull` → (필요시) `npm install`/`prisma generate` → `tsc --noEmit` 통과 시에만
  `pm2 reload shared-api`까지 수행한다(`~/shared-api-autodeploy.sh`). 즉 **`main`에 push하는
  순간이 곧 배포 시점**이다. 별도로 사람이 SSH로 들어가 수동 재시작할 필요가 없고, 그렇게
  해서도 안 된다(자동배포와 수동 조작이 겹치면 상태가 꼬인다).
- **ai_mp(프론트)**: `master`에 push하면 Vercel이 자동으로 빌드한다. Production Branch가
  `master`이므로 빌드 성공 시 자동으로 프로덕션에 반영된다(별도 "Promote to Production"
  클릭이 필요 없는 구성 — 다만 프로젝트 설정이 바뀌어 Promote가 필요한 상태라면 그 클릭은
  여전히 사용자가 직접 한다).
- 따라서 **`main`/`master`로의 머지는 그 자체가 운영 배포 행위**다. 이 프로젝트에서
  "커밋만 하고 아직 배포는 안 했다"는 상태는 `feature/learning-coach`에 머무는 동안에만
  성립하며, main/master에 올라가는 순간 존재하지 않는다.

### ★머지는 사용자 승인 후에만 — 임의로 병합하지 않는다

- `feature/learning-coach`에서 아무리 많은 커밋을 쌓아도, **`main`/`master`로 머지하는
  작업은 매번 별도로 사용자 확인을 받는다.** "지난번에 배포 승인을 받았으니 이번에도
  괜찮겠지"라고 넘겨짚지 않는다 — 자동배포 구조에서는 머지=배포이므로, 이는 실질적으로
  매번 배포 승인을 받는 것과 같다.
- 승인 요청 시 무엇이 머지되는지(변경 파일 목록 또는 커밋 로그)를 함께 제시한다.
- 사용자가 명시적으로 "이번 묶음은 완료되면 바로 머지해도 된다"처럼 사전 승인을 준 경우가
  아니라면, 묶음 하나를 완성했다고 해서 자동으로 머지하지 않는다. 완료 보고 후 지시를
  기다린다.

### 배포 순서 (반드시 이 순서)

```
1. DB 마이그레이션 (서버1 aichat) — 실행 전 사용자 승인 필수
2. shared-api 배포 (feature 브랜치 → main 머지 + push, 사용자 승인 후) — 자동배포로 반영
3. 프론트엔드 배포 (feature 브랜치 → master 머지 + push, 사용자 승인 후) — Vercel 자동 반영
```

프론트를 먼저 배포하면 존재하지 않는 API를 호출해 오류가 난다. DB가 준비되지 않은 채
shared-api를 배포하면 새 컬럼/테이블 참조가 런타임 에러를 낸다.

### 마이그레이션

- DDL 파일은 서버2에서 작성하되, **실행은 서버1의 운영 DB(`aichat`)에 대한 것이다.** 임의로 실행하지 않는다
- 실행 전 사용자에게 다음을 보고하고 승인을 받는다: 실행할 SQL 전문, 영향 테이블, 백업 여부
- DDL에 `ALTER TABLE` 또는 `DROP`이 기존 테이블 대상으로 포함되면 **즉시 멈추고 보고한다**

### pm2 재시작 주의

`shared-api` 재시작(자동배포에 의한 reload 포함)은 **학습코칭과 무관한 기존 API를 순간적으로 함께 재시작시킨다** (pm2 reload는 무중단 방식이라 완전 중단은 아니지만, 재시작 자체는 발생한다). main 머지가 이 재시작을 유발하므로, 머지 승인은 곧 이 영향까지 감수하는 결정이다.

### Cron

- ★서버1 자체 crontab이 서버1 `shared-api`의 `localhost:3020` 엔드포인트를 직접 호출한다
  (기존 `stock-worker`, `used-item-worker` 등과 동일 패턴, `~/aimp-cron.log`로 실패만 기록).
  **"서버2 crontab이 호출한다"는 이전 서술은 부정확했다** — 2026-08-11 통합검증 때 실제
  `crontab -l`(서버1)과 `work_index.md`로 확인해 정정. 새 워커를 크론에 등록할 때는
  서버1 crontab에 `* * * * * curl -sf -m 55 -X POST -o /dev/null
  http://localhost:3020/api/aimp/internal-cron/{워커명} || echo ... FAIL >>
  ~/aimp-cron.log` 형태로 추가한다(등록 전 `crontab -l`을 백업 파일로 남긴다).
- 기존 `internal-cron.ts`의 시크릿 헤더 검증 패턴(`requireCronSecret`)을 그대로 따른다. 새로 설계하지 않는다
- 인증 없는 엔드포인트를 만들지 않는다

### 롤백

- 배포 전 안정 시점에 태그(`pre-learning-d` 등)를 남겨두면, 문제 발생 시 `git revert`
  또는(불가피한 경우만, 사용자 승인 하에) `git reset --hard` + force-push로 되돌릴 수
  있다. 절차 상세는 `PROGRESS.md`의 "롤백 지점" 절 참조.

## 기존 코드 보호 원칙

이건 신규 프로젝트가 아니라 **이미 운영 중인 사이트**다.

- 기존 파일 수정 시 **페르소나 기능 키 등록과 라우트 분기 추가**로만 표현한다
- 기존 테이블의 스키마를 변경하지 않는다. 신규 테이블만 추가한다
- 신규 모델은 `Lc` 접두사 + PascalCase(`LcGoal`, `LcDailyTask`), 컬럼은 camelCase — 기존 관례를 따른다
- Prisma 스키마는 **`shared-api/prisma/schema.prisma`에만** 추가한다. `ai_mp/prisma/schema.prisma`는 오래된 사본이므로 **절대 수정하지 않는다**
- 신규 API는 `shared-api`에 Express 라우트로 구현하고 `requireAuth`를 재사용한다. Vercel 서버리스 함수(`ai_mp/api/`)는 건드리지 않는다
- 프론트는 기존 수동 라우팅 패턴을 따른다. **React Router를 도입하지 않는다**
- 신규 화면 컴포넌트는 `App.tsx`에 넣지 말고 별도 파일로 분리한다
- 기존 공용 컴포넌트를 수정해야 할 것 같으면 멈추고 물어본다
- 수정한 기존 페르소나 기능이 그대로 동작하는지 반드시 확인한다

## 개발 순서

1. 코드베이스 조사 및 보고 (0장)
2. 마이그레이션 작성 → `lc_*` 테이블 + 인덱스
3. 페르소나 카드 추가 + `/learning` 랜딩
4. 온보딩 (비로그인 입력 → 로그인 → 계획 복원)
5. 커리큘럼 생성 및 확정 + daily_tasks 배정
6. 대시보드
7. 학습 본문 + 퀴즈 + 서버 채점
8. 간격 반복 + 오답 노트
9. Cron + 알림 (웹 푸시, 이메일 폴백)
10. 주간 리포트
11. 반응형 마감 (360px 기준)
12. 테스트 및 완료 조건 검증

각 단계가 끝나면 빌드와 테스트를 돌리고 커밋한다.

## 기술 규칙

- TypeScript strict. `any` 금지.
- ORM은 기존 것을 쓰고, 없으면 Drizzle로 통일한다. **마이그레이션 파일은 반드시 버전 관리한다.** 프로덕션에서 직접 DDL을 실행하지 않는다.
- 인증은 기존 것을 재사용한다. 새 인증 시스템을 만들지 않는다.
- 세션 사용자 ID는 항상 서버 세션에서 읽는다. 클라이언트가 보낸 `user_id`를 신뢰하지 않는다.
- 모든 데이터 접근은 `lib/learning/auth.ts`의 `assertOwnership`을 거친다.
- AI 호출은 `lib/learning/ai/`에 목적별로 분리하고, 프롬프트는 `lib/learning/ai/prompts/`에 상수로 둔다. 컴포넌트에 프롬프트를 인라인하지 않는다.
- 구조화 출력은 zod로 검증하고 실패 시 최대 2회 재시도한다.
- API 키는 서버 사이드 전용. 클라이언트 번들에 절대 포함하지 않는다.
- 간격 반복은 직접 구현한다. 외부 라이브러리 금지.
- 신규 UI는 기존 디자인 토큰을 따른다. 별도의 시각 체계나 폰트를 도입하지 않는다.

## 비용 규칙 (중요)

`PRD.md` 11장에 명시하는 구현을 완료로 인정하지 않는다.

- 생성된 학습 본문·문항을 다시 생성하지 않는다
- 객관식 채점에 AI를 쓰지 않는다
- 질문하기를 일일 한도로 제한하고, 우회 경로를 만들지 않는다
- 모든 AI 호출을 예외 없이 `lc_ai_usage_log`에 기록한다

- 통합: 온보딩 → 확정 → 오늘의 학습 → 퀴즈 제출 → 복습 예약
- 보안: 타 사용자 리소스 접근 차단
- 회귀: 기존 페르소나 기능 정상 동작
- 시드 스크립트로 전체 시나리오를 재현할 수 있어야 한다

---

## 커밋

- 기능 단위로 잘게 나눈다
- 형식: `feat(learning): 커리큘럼 생성 API`, `fix(learning): 복습 항목 중복 배정`
- 빌드가 깨진 상태로 커밋하지 않는다
